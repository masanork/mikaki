# FIDO2 Server run with explicit MDS 3.0 compatibility, 2026-09-28

Tools 1.9.2 on macOS passed all **155 mandatory cases**, with **0 failures**, in **4.61 seconds** against `http://localhost:8082`. All Server Tests were selected, optional algorithms/attestations were unselected, and AUTOSCROLL was enabled after the tool reset. The run used the Rust native release server, file-backed SQLite WAL with `synchronous=FULL`, and explicit `FIDO_MDS_PROFILE=mds3.0`. The UI subsequently showed another successful 155/0 run at 3.55 seconds following user interaction. Neither duration is a comparative benchmark. Results were not submitted to FIDO Alliance by this task.

## Official service investigation

The [FIDO MDS changelog](https://fidoalliance.org/mds-changelog/) announces MDS 3.1.1 updates on May 26, 2026. The [official MDS overview](https://fidoalliance.org/metadata/) links to `https://mds3.fidoalliance.org/`. The production BLOB fetched on this date had number 286, 518 entries, `nextUpdate` 2026-10-01, and three `x5c` certificates, but no JWT header `iat`. This was an inspection of the header/payload, not a production trust validation or integration.

The [official server-test guide](https://github.com/fido-alliance/conformance-test-tools-resources/blob/main/docs/FIDO2/Server/README.md) directs users to the MDS3 conformance service. No separately documented test endpoint returning the MDS 3.1.1 required header `iat` was found in the pages and resource documentation inspected. The currently used `https://mds3.fido.tools/getEndpoints` returned five test BLOBs without `iat`, including when registering the former port 8080. This does not establish that no other service exists.

The default verifier correctly rejects missing `iat` under [MDS 3.1.1 section 3.1.7](https://fidoalliance.org/specs/mds/fido-metadata-service-v3.1.1-ps-20260105.html#metadata-blob). [MDS 3.0](https://fidoalliance.org/specs/mds/fido-metadata-service-v3.0-ps-20210518.html) did not specify that header requirement.

## Secondary test-service defect

Port 8081's positive BLOB had a 63-byte raw ES256 signature, rather than the required 64 bytes. An independent Node/OpenSSL diagnostic verified it only when the missing leading zero of the 31-byte `r` component was supplied. That diagnostic was not used as input to the verifier. The original BLOB remained rejected; re-fetching reproduced the issue. Port 8080's positive BLOB had a valid 64-byte signature. Registering port 8082 supplied correctly encoded input without modifying or re-signing any BLOB.

Ignored diagnostic data is retained in `target/fido-investigate-malformed-signature-8081.json`. The conformance cache in `target/fido-mds` now belongs to port 8082.

## Verification and boundary

Both native and Wasm accepted only BLOB 0, number 42, with 100 WebAuthn entries, after certificate path, time, pinned root, CRL, and signature verification. The four negative BLOBs were rejected for signature, CRL discovery/path, certificate path, or revocation failures. The disallowed external CRL host for the wrong-chain BLOB remains disallowed. Both implementations returned identical verified metadata.

The MDS 3.0 profile is explicitly selected through trusted startup configuration. It permits an absent `iat`, reports `issued_at: null`, and requires a signed `nextUpdate` that has not passed UTC midnight. Present `iat` must remain an unsigned integer. The strict default continues to reject the same legacy cache, and servers now refuse startup if no BLOB is verified. There is no content-based or cache-based automatic downgrade.

Native and Wasm core checks passed 27 tests each and four compile-fail doctests each. The native persistent server passed its two transaction/storage regressions. Clippy with warnings denied, Node TypeScript checking, formatting, and diff checks passed. The official full native run reached and passed all mandatory MDS and registration/assertion cases. The full GUI suite was not run against the Wasm HTTP adapter in this session.

This run establishes the selected mandatory suite under MDS 3.0 compatibility, not MDS 3.1.1 conformance or formal certification. [Startup commands](README.md#mds-version-profiles) document the explicit profile.

The process was still listening, but new `/attestation/options` requests were rejected by the user-count check. Restarting on the same port creates a fresh disposable SQLite file and restores registration; it does not delete the previous database. The restarted server log is `target/fido-native-2026-09-28-8082-restart.log`.

The official GUI suite passed again after restart: **155 passes, 0 failures, 4.77 seconds**, with the same mandatory selection and optional tests unselected. The restarted server remains listening on port 8082. The capacity limit remains, so sufficiently many repeated runs require another server restart; the GUI RESET button does not clear server-side registrations.
