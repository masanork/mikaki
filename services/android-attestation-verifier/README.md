# Android native attestation verifier

This independent JVM service implements the private `android-key-attestation-verification-v1` → `android-key-attestation-verdict-v1` contract of [the Issuer attester broker](../../docs/identity-card-issuance.md#native-attester-enrollment-broker). It verifies Android evidence; the broker issues the OID4VCI client/key attestation JWTs and owns challenge expiry, replay, instance authentication and issuer nonce binding. The verifier has no signing secret, account access or credential storage.

The Android-recommended [official Kotlin verifier](https://github.com/android/keyattestation) is pinned to **3f550f94a9e3c010dda7cdcad8bca764cd76d4f4**. The build checks the checkout revision, tracked changes and untracked source files. Source is built through a Gradle composite; it is not copied or modified in this repository. Runtime Bouncy Castle is explicitly fixed to **1.86**, overriding the upstream runtime dependency on 1.78.1, with a service-local dependency lock. Java 21 is required. The service's checksum-pinned Gradle 9.8.1 wrapper is used locally, in CI and in the container; builds no longer depend on the Android app or the upstream Gradle 8.10 wrapper. Dependabot monitors this service's wrapper and dependencies. The upstream Apache-2.0 licence is included under `licenses/android-keyattestation` in the distribution; no third-party source is vendored here.

## Verification policy

`node scripts/check-upstream-pins.ts` checks that Gradle, the container and verdict policy use the same source revision, and that the native/Wasm RSA providers use the same release. `--remote` compares the pin with upstream `main` and checks for a stable release replacing the RSA release candidate. The weekly `upstream-source-pins` workflow fails when a new source revision or applicable stable RSA release needs review; it never changes production pins automatically. The current source pin was verified against upstream `main` on 2026-10-09. The update from `55c3504` only adds Apache-2.0 licence metadata to the generated upstream POM; verifier source, roots and dependencies are unchanged. The source revision is part of the policy hash, so provisioning a build at the new pin still requires recomputing and registering its policy identifier.

Production `main` uses only the Google roots generated by the pinned upstream `roots.json`. There is no HTTP, environment or policy option to trust a caller-provided root or bypass hardware, app or revocation checks. Before deployment, review the built roots against [Android's published root set](https://developer.android.com/privacy-and-security/security-key-attestation#root_certificates), including root rotations. Root changes require a reviewed upstream update and build. The service accepts a full leaf-first chain including the exact pinned root, bounded to 2–8 distinct certificates, 8 KiB per certificate and 32 KiB total. Upstream currently requires at least three chain members. Unsupported critical extensions, weak signature algorithms and undersized/unsupported CA public keys fail closed. It uses the official verifier's Android-specific certificate validity rules, including legacy factory certificate expiry handling; it does not replace these rules with TLS PKIX validation.

The policy requires:

- An exact 32-byte challenge, canonical public P-256 JWK and equality with the **verified** attested public key. No private JWK fields or unknown envelope fields.
- Consistent TEE or StrongBox security levels, matched against the official certificate-chain security-level check; generated P-256/256-bit signing-only keys, SHA-256 digest and hardware enforcement of key attributes. The native app currently creates `noAuthRequired` keys. These keys do not demonstrate fresh biometric/PIN authentication.
- Locked device, Verified Boot, 32-byte boot key/hash, and configured minimum hardware-reported OS version and OS/vendor/boot patch month; missing, old or future patch months fail closed.
- Exactly one allowed package, minimum package version, and every reported signing-certificate SHA-256 digest in the configured allowlist. UnknownPackage and shared-UID extra packages are rejected. Unique IDs and Android device-identification attributes are rejected.
- Canonical DER attestation description and strictly increasing, unique AuthorizationList tags. This supplements upstream's normalization into a map, so a duplicate tag cannot overwrite an earlier value.

Neither TEE nor StrongBox is converted into ISO 18045 assurance, `key_storage` or `user_authentication` OID4VCI claims. Only the matched context/public key and an expiry are returned to the broker, with a maximum verdict lifetime of 60 seconds.

## Google certificate status

The only network status source is `https://android.googleapis.com/attestation/status`. TLS uses the JVM's system trust; redirects are disabled. Both **REVOKED and SUSPENDED** serials are blocked, including the supplied root. Unlike the upstream convenience fetcher, which extracts REVOKED only, this service strictly validates Google's status schema and rejects unknown statuses, duplicate JSON fields, oversized data, HTTP/content-type failures and stale responses.

Public status snapshots are cached under a synchronized loader. Cache-Control max-age minus HTTP Age bounds freshness, further capped by the policy's 60–3,600-second refresh interval. `no-store`, `no-cache`, expired age or ambiguous max-age fail closed. This interval limits time since retrieval, while respecting Google's HTTP cache freshness; it does not claim a publication age below that interval. There is no stale-on-error fallback. Network connection/read timeouts are two seconds; the bounded 1 MiB body loop has a four-second deadline checked between reads (one read timeout may extend this). Verdict expiry cannot outlive the snapshot. Tests never substitute an empty revocation list for a failed production download.

## Build and test

```sh
git clone https://github.com/android/keyattestation /private/tmp/mikaki-android-keyattestation
git -C /private/tmp/mikaki-android-keyattestation checkout --detach 3f550f94a9e3c010dda7cdcad8bca764cd76d4f4
export MIKAKI_KEYATTESTATION_CHECKOUT=/private/tmp/mikaki-android-keyattestation
export JAVA_HOME=/path/to/jdk21
services/android-attestation-verifier/gradlew --no-daemon -p services/android-attestation-verifier test installDist integrationClasspath
node --test local/conformance/android-verifier-bridge.test.ts
# Requires the current Rust Worker build (crates/worker/build/index.js + index_bg.wasm).
node --test local/conformance/identity-attester-jvm.test.ts
```

Seven JVM tests exercise real official-library verification of signed synthetic factory and RKP chains for both purposes, key/challenge/context/signature/root mismatch, app/version/signature identity, hardware/boot/patch downgrades, REVOKED/SUSPENDED/stale status, cache refresh failure, ambiguous signed tags and the actual authenticated HTTP handler. Synthetic roots and a deterministic clock are injectable only through internal test constructors; production `main` exposes neither. The Workerd bridge test checks pinned HTTPS destination, secret injection, header stripping, redirects, response media/size, body size and the eight-second timeout.

The combined `identity-attester-jvm.test.ts` now runs the actual Rust broker and D1 migrations in workerd, the unmodified private bridge through a Service Binding, and the actual authenticated JVM HTTP handler/Google verifier. A test-only transport adapter connects the bridge's fixed HTTPS destination to JVM loopback HTTP; it never generates a verdict. Fresh synthetic factory and RKP certificates bind public wallet keys and real broker challenges. A separate signing authority issues client/holder JWTs, checked independently with `jose`. Wrong app identity, certificate signature tampering, revoked/stale/unavailable status issue no JWT and leave the challenge unconsumed. Replay is rejected, concurrent redemption has one winner, and holder attestation binds the credential nonce without consuming it. Caller authorization is stripped and the bridge supplies its dedicated secret.

`IntegrationFixtureKt` lives in test classes only and is absent from the production JAR/distribution. Its bounded stdin controls generate certificates for public keys and change synthetic status; there is no fixture-root, certificate-minting or status-override configuration in production `main`. The fixture is not a native wallet and the test adapter does not qualify production TLS ingress. Physical Android, Google-issued attestation, Google network status, release signing identity and Wallet certification still need separate testing.

The build emits `build/install/mikaki-android-attestation-verifier`. The Docker build and non-root policy-hash smoke check pass; host and container policy hashes match. A container recipe is available:

```sh
docker build -t mikaki-android-attestation-verifier:local services/android-attestation-verifier
```

## Provisioning and private connection

Provide a read-only policy file through `MIKAKI_ANDROID_POLICY_FILE`, for example:

```json
{
  "format": "mikaki-android-verifier-policy-v1",
  "client_id": "operator-registered-native-wallet",
  "package_name": "app.tossa.mikaki",
  "signing_certificate_sha256": ["REPLACE_WITH_64_LOWERCASE_HEX_RELEASE_CERTIFICATE_DIGEST"],
  "minimum_version": 1,
  "minimum_os_version": 140000,
  "minimum_os_patch": "2026-09",
  "minimum_vendor_patch": "2026-09",
  "minimum_boot_patch": "2026-09",
  "security_level": "tee",
  "max_status_age_seconds": 900
}
```

Choose release signing digests and thresholds from the actual registered app/security policy. The placeholder above intentionally cannot parse. OS versions use the Android encoded value (for example 140000), package versions are integer version codes, and patch thresholds are `YYYY-MM`. A signing digest is SHA-256 of the app signing certificate DER. Allowlist entries can cover an explicitly approved signing-key rotation; every presented digest must be approved. Each service instance serves one client policy.

Run the built launcher with `--policy-hash` to print the public 43-character policy identifier. It hashes the exact policy bytes, wrapper profile version, pinned upstream revision, runtime Bouncy Castle version and sorted Google root fingerprints. Configure that same identifier in the Issuer's `IDENTITY_ATTESTER_CLIENTS[].verifier_policy_hash`. Whitespace changes to the file intentionally change the identifier. Change the wrapper profile version when its verification semantics change.

Normal launch also requires `MIKAKI_ANDROID_VERIFIER_TOKEN`, a freshly generated canonical base64url 32-byte secret, shared only with the private bridge. The service binds `127.0.0.1:8080` by default; the container binds `0.0.0.0:8080` as a non-root UID. Put it behind an operator-controlled HTTPS ingress. Configure the bridge's `ANDROID_VERIFIER_URL` to the exact `https://your-verifier/verify` endpoint and provision `ANDROID_VERIFIER_TOKEN` as a Cloudflare secret. The bridge's Workers.dev and preview URLs are disabled. Bind that Worker as `IDENTITY_ANDROID_VERIFIER` in the Issuer; no public caller URL is selected by a request. The bridge accepts only POST `/verify`, strips caller authorization/cookies/client JWTs and inserts the dedicated bearer secret. It has an eight-second upstream timeout and enforces the broker's 64 KiB input / 4 KiB response bounds. No supplied request headers are forwarded.

The JVM HTTP handler requires that secret before reading a body, permits only the exact POST `/verify`, caps JSON at 64 KiB and rejects duplicate/unknown fields. Its executor has four threads and an eight-request queue; request/response time limits are five seconds. Errors are fixed JSON with no certificate, challenge or exception details, and responses use no-store. Evidence is not logged or persisted. No service, binding, token, real signing digest or identity feature has been enabled in production by this checkpoint.
