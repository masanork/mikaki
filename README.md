# sakimori

Rustで実装する、小さく検証可能なPasskey認証基盤。個人Vaultと、利用者が許可したアプリ・AIからのデータ利用へ段階的に育てる。

tossa・tsudoiが必要とする認証と、WebAuthn PRF拡張を利用したクライアント側の鍵導出を出発点とする。必要な機能を、仕様・実装・検証を揃えて一つずつ育てる。

本書は2026-09-22時点の開発方針を記録する。実装済み機能や安全性の認証を示すものではない。

**開発中の試作です。本番サービスとして公開・運用しておらず、アカウントや利用者データを保護する目的では使わないでください。**

セッション期限等の運用パラメーターは設定へ分離する。[統合設定見本](config/runtime-policy.example.toml)と[設定変更の適用契約](docs/runtime-configuration.md)を参照する。ローカル実装では検証済み設定をビルド時に読み込む。本番用の設定適用・履歴管理は未実装。

[ローカルの認証縦切り実装](local/README.md)で、招待登録・Passkey・OIDC・RPセッション・ログアウトまで接続した。Svelte 5とTypeScript 7（svelte-check --tsgo）を使用する。起動手順、検証範囲、本番公開前に残る事項は同文書を参照する。

初期OIDCの設計一式と実装順・公開条件は[実装基準と受入計画](docs/oidc-implementation-readiness.md)に集約した。[運用制限・障害復旧](docs/oidc-operations.md)、[原子操作のSQL模型](design/sql/oidc-critical-schema.sql)、ローカルの[SQL試験](scripts/test_oidc_sql.py)と[設定検証](scripts/check_design.py)を含む。SQL模型は本番migrationやD1での実測の代わりではない。

[ES256/JOSE・ローカルD1の技術検証](design/probes/README.md)を追加し、Native/Wasm相互運用とworkerd上のbatchを確認した。公開RFC鍵と合成データによる試作であり、製品ログインや遠隔D1の検証は未完了。登録・管理者bootstrap・初期復旧なしの決定は[ADR 0005](docs/adr/0005-invitation-bootstrap-and-recovery.md)を参照する。

具体的な実装範囲、crate構成、状態遷移、受入試験、未決事項の着手ゲートは[実装仕様（Draft 5）](docs/implementation-spec.md)を参照する。ADR・分野別仕様・実装案の関係と決定状態は[文書案内](docs/README.md)にまとめる。

開発の最優先事項はコンパクトで洗練された実装の提供とする。sakimoriを継続し、native/Wasm共通のWebAuthnコアを磨いてからVaultの独自価値へ進む。[ADR 0006](docs/adr/0006-compact-portable-webauthn.md)と[コアの検証・実装順](crates/webauthn/README.md)を参照する。

2026-09-22、公式FIDO2 Server Conformance Tools 1.9.1の必須155件をnative/Wasm双方で全通過した。[試験条件・結果](local/conformance/results-2026-09-22.md)を参照。追加OPTIONAL項目と正式認証は含まない。

## 目的

- 認証に関わる判断と状態遷移を、少人数で理解・検証できる規模に保つ。
- Rustの型と可視性で誤った組み合わせを制限し、型では保証できない性質は実行時検証・競合試験・形式的手法で確かめる。
- 初版はCloudflare Workers上で動作させ、tossa・tsudoiから共通の方法で利用する。
- 初期からOIDCによる共通ログインを提供し、将来のコンテナ実行に備えて認証の中核を実行環境から独立させる。
- 認証coreから独立した個人Vaultで、暗号化データの端末間同期と、アプリをまたいだ会話の保管を実現する。
- 異なるCloudflareアカウントに配備したsakimori同士を連合し、DIDで識別した主体間のE2EEメッセージ配送を実現する。
- 将来は、対象・操作・期限を限定した委任により、agentic AIから個人VaultへMCPでアクセスできるようにする。

規格の対応数や機能一覧の長さを完成度の指標にしない。実際に使う経路について、何を保証し、どのように確認したかを説明できることを重視する。

## 前提と採用方針

- scratchから設計・実装する。monban・iwatoの現有コードや構成を維持する必要はない。
- tossa・tsudoiは未運用であり、既存データ・credential・APIとの後方互換性を要求しない。両アプリをsakimoriの仕様に合わせる。
- monban・iwatoの仕様上の知見や検証資産は参照するが、実装を正解とみなさない。仕様と独立した試験でも照合する。
- `webauthn-rs`は採用しない。
- 暗号プリミティブは保守されるライブラリを利用し、独自に設計・実装しない。採用依存の利用条件・対応ターゲット・保守状況を確認する。
- Rust採用やPure Rustであることだけを、安全性の根拠にしない。

数年以内のPQC移行を設計条件とし、[暗号方式の移行方針](docs/crypto-agility.md)に従う。初期の方式限定は維持しつつ、鍵・データ形式・クライアント登録を特定方式へ固定しない。

## 最初に実装する認証基盤

| 項目 | 方針 |
| --- | --- |
| 認証方式 | Passkeyのみ。User Verification（UV）必須 |
| 新規credential | Discoverable credential必須 |
| 署名アルゴリズム | 製品の既定はES256。検証器はEd25519・RS256・RS1も扱う（[ADR 0008](docs/adr/0008-webauthn-conformance.md)） |
| Attestation | 要求の既定は`none`。検証はnoneとES256 packed selfに対応（[ADR 0007](docs/adr/0007-packed-self-attestation.md)）。証明書・MDS検証は持たない |
| 登録・認証 | 登録開始／完了、認証開始／完了 |
| 認証器管理 | 複数登録、一覧、削除 |
| 鍵導出 | WebAuthn PRF拡張を利用したブラウザ内の鍵導出・データ暗号鍵の保護 |
| 実行環境 | RustをWasmへコンパイルし、Cloudflare Workersで実行 |
| 永続化 | D1 |
| アプリとの接続 | 本番ログインはOIDC Code＋PKCE。認証coreの内部呼び出しはService Binding |

ES256・UV・Discoverable credentialの条件を満たさない認証器は初版の対象外とする。互換性のための検証緩和や暗黙のフォールバックは設けない。

認証単体の検証は隔離した配置で行う。本番ではインスタンスごとにsakimoriの共通アカウントを設け、tossa・tsudoiの通常ログインもこのアカウントを利用する。RP IDと認証・解錠originをインスタンスごとに固定し、クライアント入力によって変更しない。汎用的なマルチテナント機構は作らない。

共通アカウントと各アプリ内のsubjectは、本人の認証とアプリ接続の許可に基づいて結び付ける。個人Vaultは必要になった時点で共通アカウントに作成し、通常ログインにVault作成・解錠を要求しない。ログインの許可とVaultの読み書き許可は別にする。異なるアプリのローカルsubjectを、アプリからの自己申告やメールアドレスだけで共通アカウントに結び付けない。決定理由と残る論点は[ADR 0001](docs/adr/0001-common-account.md)を参照する。

## アプリとの責任分担

sakimoriはcredentialと共通アカウント（AccountId）の対応、WebAuthnの検証、challengeの期限・一回性を管理する。アプリ内の主体（SubjectId）はAccountIdと区別し、メールアドレスや表示名から自動的に同一人物と判断しない。

tossa・tsudoiは次を管理する。

- アプリへの参加を許可する相手と条件。共通アカウントの登録許可・認証器の追加削除はsakimori側で管理する。
- アプリセッション、組織・役割・チケットなどの業務上の権限。
- データの意味・業務上の利用と、Vaultへの取り込み処理。暗号文・鍵を包んだデータの共通保管と同期は、個人Vaultの責任とする。
- アプリ内データや参加権限の復旧。共通アカウントとVaultの復旧方針はsakimori側で定める。

Service Bindingの呼び出し元は信頼境界に含まれる。共通アカウントの認証器追加・削除を一般の連携アプリの権限に含めない。管理操作はsakimoriの入口で本人の認証と許可を確認する。ブラウザから受けたAccountId・subjectや操作をそのまま転送するAPIにしない。

P0の認証core検証では、私的なService Bindingと検証用画面を使う。本番の共通ログインではsakimoriの認証画面を設け、sakimoriの認証手順とブラウザセッションを結び付ける。アプリ側のセッション・CSRF対策と、ログイン結果の受け渡しも統合試験の対象とする。最初の本番接続からOIDC Code＋PKCEを採用する。初回の接続確認は認証画面に統合し、許可済みアプリには有効なsakimoriセッションで戻れるようにする。詳細は[初期OIDCとログインUX](docs/oidc-login.md)に定め、G1で実装契約を確定する。

## PRFと暗号化データ

PRFは付加的な将来機能ではなく、初版の検証範囲に含める。認証の成功と、暗号化データを復号できることは区別して扱う。

- PRFの秘密出力と導出した秘密鍵はブラウザ内に保持し、認証リクエスト・ログ・サーバー保存データに含めない。
- PRF出力から、用途・アプリ・形式のバージョンを区別して鍵を導出する。鍵導出と暗号形式の具体仕様は、実装前に固定してテストベクトルを用意する。
- ランダムに生成したデータ暗号鍵を、PRF由来の鍵で認証付き暗号化して保護する。PRF出力を直接、すべてのデータの共通暗号鍵として扱わない。
- 別のPasskeyから同じPRF出力が得られると仮定しない。追加認証器には、許可された既存の復号経路を使って同じデータ暗号鍵を再度包む手順を設ける。
- PRF非対応・評価失敗を明示的な結果として扱う。鍵保護が必要な操作では失敗させ、弱い鍵導出に自動的に切り替えない。Passkey認証自体の可否とは区別する。
- `clientExtensionResults`の自己申告だけを、サーバーに対する本人確認や鍵所有の証明に使わない。
- 再ログイン後の復号、認証器追加後の復号、誤った鍵や改変データの拒否までを一連の機能として検証する。

認証器を削除しても、その認証器や利用者が過去に得たデータ暗号鍵・平文を取り消せるわけではない。将来データへのアクセスを止めるための鍵更新と、過去データに対する限界を区別して仕様化する。

全認証器を紛失した場合、別の復号経路がなければデータは復号できない。ログインの復旧だけで暗号化データも復旧したように扱わない。初版で復旧手段を設けない場合は、その制約を利用者に明示する。

## crateと依存の境界

認証基盤は次の3 crateを基本とする。

| crate | 責任 |
| --- | --- |
| `sakimori-webauthn` | WebAuthnの解析、COSE鍵・署名・origin・RP ID・UP/UVなどの検証 |
| `sakimori-auth` | 登録・認証手順、AccountIdとの結び付け、credential管理、永続化の契約 |
| `sakimori-worker` | Service Binding受付、設定検証、D1実装、時刻・乱数の供給 |

依存方向は `worker → auth → webauthn` とする。ブラウザ側のPRF・鍵保護処理は、別の小さなJS/TSモジュールとして扱う。ブラウザ側の実装言語までRustに統一することは要求しない。

G1でOIDC実装に着手した時点で`sakimori-oidc`を追加し、`worker → oidc → auth → webauthn`とする。G0の3 crate構成と区別し、空crateは先行作成しない。責任と依存候補は[実装基準](docs/oidc-implementation-readiness.md)に定める。

- WebAuthn検証器はDB・HTTP・Workersを知らない。検証した事実を返し、ユーザーの業務権限を判断しない。
- 認証coreにWorkers・D1・Axumの型を持ち込まない。時刻・乱数・永続化は境界から供給する。
- 検証済み・認証済みの型はフィールドを非公開にする。無検証の公開コンストラクタやデシリアライズ経路を設けない。
- HTTPアダプターは入力の制限・変換とサービス呼び出し、応答への変換を担当する。認証手順や判断を複製しない。
- 自作Rustコードでは原則 `unsafe` を禁止する。依存内のunsafeやFFIは別途評価する。
- crate数を増やす前に、非公開モジュールと狭い公開APIで表現できるかを確認する。

Vault・会話アーカイブ・連合メッセージング・MCPは認証coreの外に置く。必要になった段階でモジュールまたはcrateを追加し、認証coreからこれらに依存しない。3 crateという数の維持を理由に、異なる責任をcoreへ詰め込まない。

後続段階では`sakimori-vault`、`sakimori-client`、`sakimori-federation`を追加する構成を基本案とする。端末側のOpenMLSと鍵保護は`client`へ置き、サーバーcrateの依存グラフに入れない。詳細な導入時期と依存方向は[実装仕様のcrate構成](docs/implementation-spec.md#4-crate構成)に定める。

## 永続化の契約

ストアの契約は、汎用CRUDの集合ではなく、認証処理が必要とする原子的操作から定める。

- 有効なchallengeは、並行する要求のうち高々一つだけが消費できる。
- challengeの目的、対象AccountId（登録・管理操作の場合）、ブラウザとの結び付け、検証条件は開始時に固定し、完了要求の入力で差し替えない。
- credentialの登録・更新・削除に必要な制約を、DB上でも維持する。
- 処理が途中で失敗した場合、本人確認やデータの永続化が未完了のまま成功を返さない。
- 通信切断や再試行で、一回限りの処理が二重に成立しない。

「消費済み」というRustの型名だけでDBの原子性を保証したとみなさない。単なるSELECT後のDELETEや、後から同期するローカル状態を一回性の根拠にしない。

初版はD1で実装する。将来のコンテナ版では組み込みTursoを有力候補として評価するが、SQLx・Tursoなどの選択を認証coreに露出させない。異なるストアには同じ契約試験を適用する。

## 検証を揃えて育てる

機能を追加する際は、利用場面、入力、許可条件、状態遷移、失敗時の挙動、検証方法を先に記述する。

初版では少なくとも次を確認する。

- 登録・認証の成功と、署名改変・不正なorigin／RP ID・UP/UV不足・credentialやsubjectの取り違えの拒否。
- challengeの期限境界・目的違い・再利用・並行二重消費の拒否。
- 不正なJSON・CBOR・COSE・長さ・深さ・重複項目を含む入力に対する制限と拒否。実装対象のパーサーにはfuzzingを適用する。
- D1を含む実行環境での登録・認証・追加・削除と、失敗・再試行時の整合性。
- 対象ブラウザ／認証器でのPRF鍵導出、再ログイン後の復号、追加認証器への鍵の受け渡し、非対応時の挙動。
- Nativeでのcoreの単体テストと、Wasmでのビルド・Workers上の統合試験。
- 外部crateから検証済み型を捏造できないことなど、重要なAPI制約のコンパイル失敗テスト。

必要な仕様範囲について適合性試験を利用する。試験を通すためだけに、製品で使わない規格や認証器形式を実装しない。適合性試験の合格を、セキュリティ全体の証明と表現しない。

KaniやTLA+などは、明示した不変条件と対象がある場合に導入する。モデルの仮定と実装の対応を確認し、ツールの導入そのものを成果としない。

## 規模を抑える

- 用途のない既存互換用コード、汎用プラグイン、DB抽象化を作らない。規格適合・具体的な相互運用に必要な暗号方式の互換実装は、[暗号方式の移行方針](docs/crypto-agility.md)に従って備える。
- IDや検証状態など、誤用が危険な箇所に型を集中させる。あらゆる値や処理段階を専用trait・型にしない。
- 自作コード行数、公開API数、依存、Wasmサイズ、公開操作数を記録し、増加の理由を変更ごとに確認する。
- 行数削減のために検証条件・失敗処理・競合試験を省かない。削る対象は不要な機能と汎用化とする。
- 依存ライブラリ内部の機能も考慮する。SimpleWebAuthnの呼び出し行数と自作検証器の行数だけを比較しない。

## 段階的な開発

1. **認証とPRF・OIDC**：登録・ログイン・鍵の解錠を検証する。本番アプリ接続にはOIDCを使う。
2. **個人Vault**：IndexedDBとR2で暗号文と包まれた鍵を保存・同期し、別端末で復元する。競合・通信失敗・削除を扱う。
3. **会話アーカイブ**：利用者が許可したtossa・tsudoiの会話を取り込み、本人が横断して参照・検索する。
4. **連合E2EEメッセージング**：独立した二つのCloudflareアカウントに配備したsakimori間で、まず1対1のテキスト配送を検証する。DIDによる識別と、端末間の暗号化を分けて設計する。
5. **MCPによる限定的な参照**：利用者が選択した範囲をAIに提供する。最初は読み取りのみとする。連合メッセージの受信はAIへの開示許可を意味しない。

各段階で必要な仕様と検証を揃える。同期・連合・アーカイブ・AI機能のために、最初の認証実装へ未使用の汎用機構を追加しない。詳細は[個人Vault・会話アーカイブ・MCPの方針](docs/personal-vault.md)と[連合E2EEメッセージングの方針](docs/federated-messaging.md)を参照する。

## 後から追加するもの

コンテナ実行は将来目標とし、初版では実装しない。空のcrateや未使用の抽象化も追加しない。OIDCの初期採用は[ADR 0002](docs/adr/0002-oidc-from-first-release.md)で確定し、必要なログイン範囲から実装する。

- OIDCの追加フローや第三者アプリへの開放は、初期のCode＋PKCEとは別に利用要件を確認する。
- コンテナ追加時は、同じ認証coreにNativeのHTTP・ストアアダプターを追加する。
- WebAuthnのRP IDとOIDCのissuerを混同しない。共通ログインへの変更は、認証器の利用範囲とPRF鍵への影響も評価する。
- 追加アルゴリズム、attestation、パスワード、SAML、OpenID Federation、SCIM、汎用マルチテナントなどは、具体的な利用要件と検証方法ができるまで追加しない。DIDベースのメッセージ連合は、OpenID Federationへの対応とは別の目標とする。

次に実装する機能は、規格の網羅性ではなく、利用者が必要とし、挙動を確認できるかで選ぶ。
