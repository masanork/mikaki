# Identity-card attributes, OID4VCI and SD-JWT/mdoc presentation

The Android Tauri client reads My Number input-support four attributes and traditional IC driving licences. It can submit the signed evidence, obtain account-owner approval in the system browser, and receive a first-party **Mikaki linked-document attribute credential** through OID4VCI 1.0 (`dc+sd-jwt` or `mso_mdoc`). This is implemented locally, disabled for production by default, and not yet qualified with physical cards. It is not a government-issued PID or mobile driving licence.

The preparation and integration checkpoints below record pre-merge work. They do not establish the current production migration ledger, feature activation or physical-device qualification; see [current source and deployment evidence](status.md).

## User flow

In Settings → Diagnostics → 身分証の読取, select the document and enter its four-digit PIN. A driving licence can be previewed with PIN1, but linking requires PIN2 as well. Both PINs are verified once per explicit read; a failed VERIFY is never retried automatically. PINs are cleared immediately from the form and never sent to the backend.

The local preview remains `unverified`. Selecting サーバーで検証して紐付ける uploads the evidence for independent server verification. The app creates a **separate P-256 holder key** (non-exportable Android Keystore key on Android, in-memory software key elsewhere), keeps protocol secrets in Rust, and opens the exact first-party approval URL. The browser requires an existing live Mikaki SSO session; if necessary, sign into Mikaki in that browser first and start again. It displays the account, derived attributes, document kind and holder-key thumbprint. Compare the thumbprint with the app before approving. The one-use browser approval links attributes to the internal account ID and authorizes this issuance.

The browser also offers 属性のみ紐付ける. This links the verified attributes but invalidates the reading app's polling authority, so that approval cannot issue a credential to its provisional holder key. Start a separate issuance from the intended wallet, as described below; the reading app's receive control explains that this path has no local issuance authority. This selection does not grant UserInfo release permission.

Return to the app and select 承認を確認して証明書を受け取る. Choose SD-JWT or mdoc before starting linkage; one grant issues one credential of the chosen format. The app performs the pre-authorized-code exchange, obtains a nonce, submits a signed `proofs.jwt`, and validates the received credential. SD-JWT checks issuer/type/signature/disclosures; mdoc checks the pinned issuer public key against the Document Signer certificate, COSE signature, MSO doctype/validity/device key and every IssuerSignedItem digest. Both formats use the existing dedicated holder key. Credentials expire within five minutes, shortened by the validity bounds described below. Android stores the receipt, its pinned issuer public key and holder-key identifier using AES-256-GCM with a separate Keystore wrapping key, fixed authenticated context and atomic writes under `noBackupFilesDir`. 保存した証明書を確認 restores it only while unexpired, after checking the existing holder public key and issuer signature again; a missing or changed holder key fails closed. Explicit local erasure removes the encrypted file, wrapping key and all identity holder keys, including orphan keys from an interrupted issuance, without touching the login/Vault DPoP key. Other platforms retain receipts only in memory. Android hardware backing, restore/deletion after process restart and NFC remain unqualified on a physical device. The holder key does not require fresh biometric authentication; the app makes no attestation or hardware-assurance claim.

紐付けた属性を確認・解除する opens the owner-only `/identity` management page. Deletion erases normalized attributes from both the linked record and its transaction, and blocks further issuance. Already-issued credentials expire within five minutes; there is no live credential-status endpoint yet. Clearing a receipt in the app only deletes local state, not the server-side linkage.

## Evidence and guarantee boundary

The shared [identity crate](../crates/identity/src/lib.rs) owns bounded APDU handling, strict parsers, issuer-signature verification and the issuance profile. Android transports `IsoDep` through the extracted madowi plugin. The licensed civ subset supplies APDU constants, four-attribute parsing, era conversion and JIS decoding. Its permissive driving-licence parser and guessed EF07 verifier are not used for verification.

- **My Number Card:** read input-support EF0002 and EF0003, never EF0001. Check SHA-256 of a complete, independently parsed four-attribute preimage against DF32, and RSA-2048 PKCS#1 v1.5 SHA-256 signature DF33 over DF31/DF32 TLVs against an explicitly configured trusted issuer key. Each accepted framing must produce exactly the same four attributes; duplicated/unsigned attributes are rejected. EF0003 includes an opaque personal-number hash (DF31), which is sent only as necessary signed evidence and is never retained. CVC chain validation and unsupported issuer generations are not inferred from a card's own key. This My Number layout follows the [madowi implementation](https://github.com/digital-go-jp/madowi/blob/f3330baf18d005aaffbfcfb0d69f667ddfc1d0e6/crates/madowi-core/src/card/kenmen_verify.rs); real-card qualification remains required.
- **Driving licence:** according to [NPA specification §4](https://www.npa.go.jp/laws/notification/koutuu/menkyo/menkyo20240719_145.pdf), verify the SHA-256 hash of the **entire** fixed-size DF1/EF01 (880 bytes), DF1/EF02 (82 bytes) and DF2/EF01 (2005 bytes), including padding, using EF07/B1 and an operator-trusted RSA-2048 public key selected by EF07/B6. Its PKCS#1 v1.5 padding contains the raw digest without DigestInfo. Photo and registered domicile require PIN2; they are never displayed, included in credentials or retained by the backend. The issued attributes come from the signed **issuance-time base EF**; unsigned change records, current licence suspension/revocation and gaiji bitmap names are not represented as verified. Invalid/unsupported gaiji and expired base licence dates fail closed.

Static signatures prove data authenticity and can be replayed from a copied card. They do not establish live possession, face matching or that the account owner is the human named on the card. The credential carries `assurance=issuer_signed_static_data`, `attributes_source`, verification time, trusted key ID, `live_possession_verified=false` and `government_credential=false`. Browser consent records the account owner's decision to link that data; it does not raise the assurance level. A later high-assurance profile needs an appropriate possession/liveness and trust/status policy before claiming identity verification.

No raw EFs, PINs, photo, registered domicile, licence number, personal number or personal-number hash are stored in D1 or logs. The derived name, address, birthdate, optional gender/expiry, provenance and holder **public** key are stored for the consent/issuance flow. Linked attributes remain until owner deletion; abandoned unlinked transactions and expired nonces are removed by the minute cron and on intake. Keep DB backups/retention aligned with this privacy boundary. New issuance requires a linked record within 24 hours, unchanged trust policy, active account and matching security epoch. Existing records are separate from editable, opaque Vault attributes, and require separate owner consent before release through profile-scoped UserInfo tokens, as described below.

## Server surface

The [Workers adapter](../crates/worker/src/identity.rs) and [migration 0036](../crates/worker/migrations/0001_owner_vault_initial.sql) implement:

| Endpoint                                                                  | Purpose                                                                                                          |
| ------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `POST /identity/intake`                                                   | Independently verify evidence and bind a random poll secret to a holder key; transaction expires in 600 seconds. |
| `GET/POST /identity/approve`                                              | Review/approve with live SSO, session-bound CSRF, exact Origin and one-use state transition.                     |
| `POST /identity/poll`                                                     | Secret-bound polling; approval releases one 90-second pre-authorized code once.                                  |
| `GET /identity`, `POST /identity/erase`                                   | Owner-only review and session-bound deletion form.                                                               |
| `GET /identity/documents`, `DELETE /identity/documents/:document`         | Owner API and same-origin deletion.                                                                              |
| `GET /.well-known/openid-credential-issuer/identity/issuer`               | Metadata for the dedicated credential issuer.                                                                    |
| `GET /.well-known/oauth-authorization-server/identity/issuer`             | Dedicated pre-authorized-code authorization-server metadata.                                                     |
| `POST /identity/issuer/token`                                             | One-use code exchange; 120-second token restricted to this issuer.                                               |
| `POST /identity/issuer/nonce`                                             | Public, rate-limited, 60-second nonce.                                                                           |
| `POST /identity/issuer/credential`                                        | One ES256 holder proof and one credential in the grant-bound SD-JWT or mdoc format.                              |
| `GET /identity/issuer/jwks`, `GET /identity/issuer/types/linked-document` | Dedicated issuer verification key and credential type metadata.                                                  |

OID4VCI follows the [1.0 Final specification](https://openid.net/specs/openid-4-verifiable-credential-issuance-1_0-final.html): plural `proofs.jwt`, `credentials`, `dc+sd-jwt`, a dedicated nonce endpoint and path-aware well-known metadata. There is no deferred issuance, multiple proofs, generic external offer import or generic external issuer support in the native app. The Issuer separately supports opt-in request/response encryption as described below; native first-party encrypted issuance reception is implemented as described below; native HAIP authorization-code issuance is available through the opt-in Android flow described below. The app checks exact configured HTTPS endpoints and does not follow redirects. Loss of an offer/token/credential response requires a fresh read and approval rather than replaying a consumed grant.

D1 CAS statements and triggers create linkage with approval atomically, verify live SSO/epoch at approval, and consume the nonce and grant atomically at issuance. Policy changes, document deletion and security-epoch changes invalidate further issuance. Ordinary OP access tokens and Vault grants have no authority on the credential endpoint. The SD-JWT credential, valid for at most five minutes, has independently salted disclosures and an explicit `cnf.jwk`; no internal account ID or raw card identifier is disclosed.

Credential validity is capped by the earliest of issuance time plus 300 seconds, the linked record’s `valid_until`, the configured government evidence-verification key’s `not_after`, and any signed physical-document expiry date. Driving licences require a valid expiry date; My Number input-support evidence does not supply a card expiry date. mdoc is additionally capped by its Document Signer certificate’s `notAfter`. Physical expiry dates use the existing UTC day-end convention; they do not establish current licence entitlement. A shorter remaining interval produces a shorter credential, and an elapsed interval prevents issuance. The final atomic D1 statement rechecks that the linkage still covers the signed expiry and that the expiry has not passed while preparing the response.

Both native receipt validators require a positive signed validity interval, reject credentials at the exclusive expiry boundary, and reject a signed credential expiry later than its disclosed physical-document expiry. Existing bounded future-issuance clock skew does not extend the expiry. These checks apply on initial receipt and restoration; they do not provide immediate revocation or determine a government card’s current status. Tests cover short linkage/trust-key lifetimes in both Worker issuance formats, short Document Signer validity, physical expiry, exact-end rejection and a correctly signed SD-JWT whose expiry exceeds its document date.

## Independent wallet issuance

[Migration 0038](../crates/worker/migrations/0001_owner_vault_initial.sql) adds a separate `identity_wallet_grant` table; [migration 0039](../crates/worker/migrations/0001_owner_vault_initial.sql) adds one-use PAR storage and DPoP token binding. Apply both before enabling the wallet profile. Set `IDENTITY_WALLET_ENABLED=true` together with `IDENTITY_ENABLED=true`, and register public wallets using `IDENTITY_WALLET_CLIENTS`, for example:

```json
[
  {
    "client_id": "test-wallet",
    "name": "Operator-approved test wallet destination",
    "redirect_uri": "https://wallet.example/callback"
  }
]
```

The feature is absent/disabled by default. The registry is limited to 32 distinct clients, each with one exact canonical HTTPS callback without query, fragment or user credentials. No custom-scheme callbacks, dynamic registration or wildcard matching are supported yet. The registry is separate from OP/Vault clients and OID4VP verifier/reader registrations. Public client IDs and displayed names do not authenticate the wallet application; the owner must have deliberately initiated issuance from the intended wallet. Client attestation and HAIP certification remain separate work.

When enabled, authorization-server metadata advertises `/identity/issuer/authorize`, `authorization_code`, `response_types_supported=["code"]`, S256 PKCE, issuer identification in authorization responses, `/identity/issuer/par` and `dpop_signing_alg_values_supported=["ES256"]`. Credential issuer metadata provides `linked_document` and, when configured, `linked_document_mdoc` scopes. This implements the wallet-initiated scope subset of [OID4VCI Final section 5.1.2](https://openid.net/specs/openid-4-verifiable-credential-issuance-1_0-final.html#section-5.1.2). Unknown scope values are ignored, but exactly one supported credential scope is required. Authorization Details, JAR, issuer-initiated offers, refresh tokens, deferred issuance and generic external-issuer reception are not implemented by this public-client addition. The separate HAIP profile adds client/key attestation as described below. The existing first-party pre-authorized flow remains available.

The wallet discovers metadata, generates its own holder key and a fresh PKCE verifier (43–128 RFC 7636 characters), and opens an authorization request such as:

```text
GET /identity/issuer/authorize?response_type=code
  &client_id=test-wallet
  &redirect_uri=https%3A%2F%2Fwallet.example%2Fcallback
  &scope=linked_document
  &code_challenge=<base64url-SHA256-of-verifier>
  &code_challenge_method=S256
  &state=<wallet-session-state>
  &resource=https%3A%2F%2Fissuer.example%2Fidentity%2Fissuer
```

Alternatively, POST those parameters as a duplicate-free form to `/identity/issuer/par`. A successful 201 returns an opaque `urn:ietf:params:oauth:request_uri:` URI and `expires_in=90`. Open `/identity/issuer/authorize` with `client_id` and `request_uri`. Authorization parameters alongside that reference cannot override the saved redirect URI, scope, state or PKCE challenge; the endpoint uses the authenticated stored PAR. Duplicate parameters and bounded-size violations remain rejected. The pushed request is bound to the registered client and current registry policy, cannot be modified in the browser, and is atomically consumed when owner approval or denial completes. Opening or revisiting the pending approval screen does not consume it. Multiple pending screens may exist, but only one decision can complete and create a code. The decision rechecks PAR expiry/current policy at the time of consent. Stored authorization parameters are scrubbed on consumption; expired rows are removed in bounded batches. PAR is optional for this public-client profile and does not authenticate a wallet.

The browser needs a live owner SSO session; it currently returns 401 instead of redirecting automatically to login. After signing in, start the request again. The owner reviews the registered destination, callback and format and explicitly selects a live linked document. No document is preselected. Approval discloses the credential's full supported attribute set; later OID4VP presentation remains selectively disclosed. Exact Origin, session-bound CSRF, current account epoch, document ownership/validity and unchanged evidence/client policies protect approval. The pending request lasts 300 seconds. A successful 303 callback carries a one-use 90-second code, the original optional state and `iss`; denial returns `error=access_denied` without a code. The wallet must check state and issuer before code exchange. Invalid/unregistered destinations never receive a redirect.

POST the code to `/identity/issuer/token` with `grant_type=authorization_code`, `client_id`, the exact `redirect_uri` and `code_verifier`. The public-wallet profile uses `token_endpoint_auth_method=none`. A wrong verifier/client/callback, expired code or changed policy cannot consume a valid code. The successful exchange consumes it atomically and yields a 120-second issuer-only token restricted to the approved configuration. An ES256 `DPoP` header binds the token to that proof key and returns `token_type=DPoP`; omitting it preserves the public-client Bearer profile. Bound tokens require `Authorization: DPoP <access_token>` and a fresh signed resource proof with exact POST credential URL, matching key thumbprint and `ath`. Missing proofs, wrong keys, Bearer fallback and proof replay fail closed. `MIKAKI_DPOP_NONCE_MODE=required` challenges token/resource requests using the existing separate AS/RS D1 nonce ledger. Grant/code exchange remains public-client authentication method none. It has no OP/UserInfo/Vault authority. Obtain `c_nonce` from the existing nonce endpoint, then send the approved `credential_configuration_id` and one `proofs.jwt` using an embedded public P-256 JWK. The issuer validates the wallet's signature, audience, nonce and freshness; optional `iss` must match the authorized client. `jti` and `exp` are optional; a supplied value remains bounded. Nonce consumption provides replay protection. Optional credential request `format`, `vct` and `doctype` fields must match the selected configuration exactly.

Authenticated authorization-code reuse revokes any remaining token authority for that code in both single-credential and multi-credential grants. A concurrent successful exchange followed by an authenticated losing exchange also leaves its token revoked. Exact client registration/policy, callback, S256 verifier, and matching accepted sender/client proofs are required before this side effect; knowledge of a code or a wrong verifier/client/key cannot cancel another grant. Already delivered credentials cannot be recalled by code replay. Local `identity-issuance.test.ts` covers the single-credential race, preserves a live grant after wrong verifier/client/callback requests, and continues normal issuance from a fresh owner-approved flow.

Apply [migration 0041](../crates/worker/migrations/0001_owner_vault_initial.sql) before updating a wallet-enabled deployment. Authorization-code DPoP binding follows [RFC 9449 §10/10.1](https://www.rfc-editor.org/rfc/rfc9449.html#section-10.1): an optional `dpop_jkt` request parameter binds the code, and a verified DPoP header at PAR implies the same binding. Both together must name the same key. The P-256 thumbprint is stored separately as `authorization_dpop_jkt` on the owner-approved grant; atomic token exchange requires that key before recording the access-token binding. A bound code cannot produce a Bearer token or a token using a substitute key. An absent PKCE verifier returns `invalid_grant` without consuming the code. PAR proofs use the AS nonce/replay ledger with exact POST/PAR URL and signature validation. A nonce challenge does not consume client-attestation PoP or create PAR state. Client-policy versions changed with this checkpoint, so pending grants/tokens from the prior binding policy cannot be exchanged under the new policy.

The credential is bound to this wallet-proven holder key, rather than the reading app's key. Successful issuance atomically records that public key, consumes the nonce and an approved issuance slot (the public-wallet token is single-use), and rechecks current linkage, epoch, policies and expiry. Neither private key nor identity attributes are copied into the wallet-grant table. Linkage deletion deletes its grants, account active/epoch changes delete all account wallet grants, and the minute cron removes expired grants in bounded batches. This prevents old issuance authority from returning after account reactivation. As elsewhere, already issued credentials remain valid until their signed expiry.

Apply [migration 0042](../crates/worker/migrations/0001_owner_vault_initial.sql) before the PAR-completion update. The consumption trigger now runs on the pending-to-approved/denied transition, alongside the atomic grant predicate that checks an unused, unexpired PAR. A consumed or expired URI returns `invalid_request_uri` to the callback only if the URI hash, supplied client, current policy and saved callback all match the current registration. Query parameters cannot replace its saved state or destination. Unknown/malformed URIs, substituted clients and changed registrations receive a local error without a redirect. Only trusted callback/state routing is retained after consumption; rows are kept for at most five minutes after expiry for these error callbacks and then removed by bounded cleanup. The client-policy version changed again, so grants created under the old consumption policy cannot be completed under this one.

Apply [migration 0043](../crates/worker/migrations/0001_owner_vault_initial.sql) before enabling the bounded-issuance update. Under HAIP, the owner explicitly authorizes up to **16** credentials of the selected configuration and linked dataset within the original **120-second** token lifetime. This is a local issuance-policy limit, not a number prescribed by HAIP. [OID4VCI Final section 8](https://openid.net/specs/openid-4-verifiable-credential-issuance-1_0.html#section-8) permits consecutive credential requests for the approved configuration/dataset. Each request still needs a fresh issuer proof nonce and a valid sender-bound DPoP proof. The counter increment, linkage/policy/expiry checks and nonce consumption are atomic; failed requests do not spend issuance slots, issuing does not extend expiry, and the final slot erases access authority. Public-wallet and first-party pre-authorized issuance retain their one-credential budgets. Existing database grants default to one slot; the HAIP policy hash changed, so old approvals cannot acquire the expanded authority. No copied attributes or private keys are added to the grant ledger.

Authenticated reuse of a redeemed HAIP code revokes its remaining multi-issuance grant, following [RFC 6749 section 4.1.2](https://www.rfc-editor.org/rfc/rfc6749.html#section-4.1.2). Only the redeemed code hash is retained, bounded by the grant lifetime. Current client registration, callback, PKCE verifier, attested instance and sender key must all match before revocation; malformed or unauthenticated requests and substitute verifiers/keys cannot cancel the live grant. This addition does not change the separate public-client single-use contract. Credential Authorization schemes are case-insensitive. Unknown noncritical DPoP header/claim extensions are ignored, while unsupported critical/unencoded-payload and remote-key header parameters and private JWK material remain rejected.

The workerd/D1 test uses genuine independently signed card evidence, a link-only owner approval, a distinct Node JOSE wallet key, PKCE authorization and both formats. Independent JOSE/CBOR/COSE checks validate the returned issuer signature and holder binding. It also exercises denial, wrong owner/CSRF/Origin/destination, configuration switching, registry changes, invalid PKCE and proof signatures, optional proof claims, code/token expiry, concurrent one-use operations, unlinking and disable/re-enable. The test additionally covers PAR expiry, duplicate parameters, unchanged policy, one-use requests and DPoP key/URL/ath binding, replay and Bearer fallback.

An opt-in JVM interoperability test uses the unchanged [Multipaz SDK at commit `b741acd`](https://github.com/openwallet-foundation/multipaz/tree/b741acd1f2a77ffbe2818b71822841781dd7ad9f). Its actual provisioning client discovers metadata, performs PAR, PKCE, DPoP nonce challenge/retry and receives both custom configurations using SDK-generated proof keys. Only the HTTP engine is bridged to local workerd; the owner browser consent is exercised with a synthetic live SSO session and independently signed synthetic card evidence. ### Key-attestation trust and proof contract

HAIP issuance now requires `IDENTITY_KEY_ATTESTATION_TRUST={"trust_anchors":["standard-base64-DER-CA"]}`. This purpose-specific configuration is independent of Wallet/client-attestation trust and credential signing PKI; no system roots, fetched keys or implicit reuse of another role's CA is accepted. Missing or invalid key trust stops credential metadata with `503 issuer_unavailable`. Changing any trust/assurance policy changes the HAIP grant policy hash, invalidating earlier PAR, approval, code and token authority. No new database migration is needed beyond the existing 0036–0043 sequence.

The Issuer supports [OID4VCI Final Appendix D/F](https://openid.net/specs/openid-4-verifiable-credential-issuance-1_0.html#appendix-D.1) with [HAIP Final section 4.5.1](https://openid.net/specs/openid4vc-high-assurance-interoperability-profile-1_0-final.html#section-4.5.1): `proofs.jwt` carrying a `key_attestation` header, and `proofs.attestation` carrying the attestation directly. Metadata advertises both with ES256 and `key_attestations_required`. In either case exactly one proof and one attested public P-256 key are accepted; multiple/ambiguous proof types and multiple attested keys are rejected, and batch issuance is not advertised. JWT proofs use embedded `jwk`; other key-resolution mechanisms are outside this subset. An unattested JWT cannot downgrade the HAIP requirement. The public-wallet and first-party profiles retain their existing JWT proof contract.

The attestation must have `typ=key-attestation+jwt`, a valid ES256 signature, a currently valid explicitly trusted x5c chain without its root, a non-self-signed digital-signature leaf, fresh `iat` and the Issuer's one-use `c_nonce`. This initial attester certificate policy requires critical Basic Constraints/Key Usage and rejects EKU-restricted certificates. For JWT proofs, attestation `exp` is mandatory and its single attested key must equal the proof's normalized signing JWK; the outer signature, issuer audience and optional authorized-client `iss` remain verified. Standalone attestations may omit `exp` as permitted by the specification. Credential validity is capped by supplied attestation expiry and the attester chain deadline in addition to the existing credential/document/evidence limits. Unknown noncritical extensions are ignored; private keys, unsupported critical/unencoded-payload/remote-key headers and attestation `status` mechanisms are rejected. Online/platform status and production attester lifecycle qualification remain outstanding.

Optional `key_storage` and `user_authentication` configuration arrays declare acceptable case-sensitive values in metadata. A signed attestation must include at least one configured value for each required component. Empty configuration/claim arrays and oversized lists fail closed; unknown strings cannot satisfy a configured requirement. Omitting these policy arrays demands a trusted attestation without claiming a particular hardware protection or user-authentication assurance level. This code does not turn synthetic attestations into Android/iOS hardware evidence.

### Native attester enrollment broker

An opt-in broker now connects native proof of key possession and Android evidence to externally verified client/key attestation JWTs. Apply migration **0044** in addition to the identity migrations. `/identity/attester/challenge` and `/identity/attester/attestation` are POST-only and require `IDENTITY_ENABLED`, `IDENTITY_WALLET_ENABLED`, `IDENTITY_HAIP_ENABLED` and **`IDENTITY_ATTESTER_ENABLED=true`**. No production configuration or deployment has enabled this broker.

Required operator configuration:

| Setting                                     | Contract                                                                                                                                                                                                                                     |
| ------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `IDENTITY_ATTESTER_CLIENTS` variable        | JSON array of 1–32 distinct `{client_id, verifier_policy_hash}` policies; the latter is a 43-character SHA-256 base64url policy identifier agreed with the verifier.                                                                         |
| `IDENTITY_ATTESTER_SIGNING` secret          | JSON `{jwk, chain, trust_anchors}`; `jwk` is a JSON **string** containing the dedicated private ES256 JWK with `kid`; certificates are canonical standard-base64 DER. The attester leaf/public key and validated chain must match.           |
| `IDENTITY_ANDROID_VERIFIER` service binding | Independently implemented Android verification service. Caller-supplied verifier URLs are never accepted.                                                                                                                                    |
| Issuer Wallet trust                         | Provision the attester's issuer URL (`MIKAKI_ISSUER` + `/identity/attester`) and CA roots in the existing client/key-attestation trust configuration. The Android platform roots belong to the verification service, not this JWT authority. |

The attester signing key must differ from the credential signing and credential encryption keys. Changes to the configured issuer, client policy, signing public key, certificate chain or CA roots invalidate pending enrollments and the old client attestation's permission to enroll holder keys. Private signing material is not part of the policy fingerprint.

Enrollment is ordered:

1. Request a `client` challenge with `{client_id, purpose:"client"}`. Generate a fresh Android instance key with that 32-byte attestation challenge, and submit its public key, `certificate_chain` and a native-signed enrollment `proof` with the returned challenge. A successful verdict yields `oauth-client-attestation+jwt` bound to this instance key and client ID, valid for at most 300 seconds. This enrollment does not authenticate an account or grant credential issuance.
2. Use the instance attestation and fresh OAuth client PoP with PAR and token exchange. After obtaining the issuer's current `c_nonce`, request a `holder` challenge with `{client_id, purpose:"holder", c_nonce}` and a fresh instance PoP addressed to the attester. Generate the fresh holder key **at this point**, with the returned Android challenge. Submit the same nonce, public key, chain and holder proof with another fresh instance PoP.
3. A successful holder verdict yields `key-attestation+jwt`, bound to that issuer nonce and holder public key, valid for at most 60 seconds and bounded by the verifier, instance attestation, signing certificate and issuer nonce deadlines. Attesting does not consume `c_nonce`; actual credential issuance does. Use the native holder key to sign the OID4VCI proof and receive the encrypted credential.

Both POST bodies use exact private API fields (unknown fields rejected). The redemption body is `{client_id, purpose, challenge, public_key, certificate_chain, proof, c_nonce?}`. The private enrollment proof has `typ=mikaki-wallet-attester-proof+jwt`, ES256/public `jwk`, and `iss=client_id`, `aud=attester`, `nonce=challenge`, `purpose`, `iat`, `exp`; it is not an OID4VCI proof. Proofs expire within 60 seconds. Challenges expire within 60 seconds, bind client/purpose/current policy and, for holders, instance thumbprint plus nonce hash. D1 stores hashes and deadlines, without raw Android chains, device IDs or JWTs. Rate limits and a 2,000-live-challenge cap apply. Redemption has one atomic winner; failed evidence/verdicts cannot issue a JWT or consume the challenge. Instance PoP replay is rejected by the existing attestation replay ledger.

The binding receives a fixed `/verify` request with `{format:"android-key-attestation-verification-v1", client_id, purpose, verifier_policy_hash, evidence:{challenge, public_key, certificate_chain}}`. It must return HTTP 200 with JSON `{format:"android-key-attestation-verdict-v1", verified:true, client_id, purpose, challenge, public_key, verifier_policy_hash, expires_at}`. Every field must match the enrollment, the verdict must remain live, unknown fields are rejected and the response is capped at 4 KiB with a 10-second deadline. Rejection, errors, redirects or malformed/mismatched verdicts fail closed. The deadline drops the pending Rust future; it does not claim cancellation of an already dispatched remote operation. The broker never derives `key_storage` or `user_authentication` claims from untrusted Android data.

### DCQL trusted-authority selection checkpoint

Final-profile credential queries now accept `trusted_authorities`, including `type: "aki"` with nonempty `values`. ## Owner-approved UserInfo attributes

Apply [migration 0037](../crates/worker/migrations/0001_owner_vault_initial.sql) and set `IDENTITY_USERINFO_ENABLED=true` together with `IDENTITY_ENABLED=true` to enable the optional `mikaki_linked_document` UserInfo claim. Both flags are required; the new flag is absent/disabled by default. Discovery advertises this claim only when enabled. Without migration 0037, disabled deployments retain the existing owner management page; enabling the claim requires that migration. The existing `profile` scope is its request envelope, and an additional owner-approved release is mandatory. Neither `openid` alone nor linking a card releases attributes to an RP. There is no new scope, claims-parameter support or ID-token claim.

On `/identity`, the owner selects an existing active connected client and explicitly checks one or more of name, address, birthdate, gender and document_expiry_date. No field is selected by default. A release permits that client's current profile-scoped tokens to retrieve the selected attributes for at most one hour, capped by the linkage validity. It replaces that client's previous document/field selection. The page also provides a separate release-revocation form. The forms require live owner SSO, exact same Origin, session/document-bound CSRF and the current registration/connection/release versions; the grant statement rechecks those facts atomically. A revoked release retains a versioned tombstone, so resubmitting an older form cannot restore permission. Client registration, connection and account epoch/active changes invalidate releases, including a connection disabled and then re-enabled.

Both Bearer and DPoP UserInfo paths return an optional object such as:

    "attributes": { "name": "試験 太郎", "birthdate": "1990-02-28" },

      "document_type": "my_number_card",

This is an application extension, not OIDC Identity Assurance `verified_claims`. The response includes no account/document IDs, raw card identifiers or unselected attributes. Every read rechecks token/session authority, profile scope, current client and connection versions, account epoch, release/linkage expiry, document revocation, current trusted-key policy and issuer-key validity. ## Signed OID4VP presentation profile

The app implements a deliberately bounded [OID4VP 1.0 Final](https://openid.net/specs/openid-4-verifiable-presentations-1_0-final.html) preregistered-client profile: paste a signed Request Object in Diagnostics, review the verifier name, exact HTTPS response URI and requested attribute values, then explicitly approve or cancel. Review makes no network request. It accepts ES256 `oauth-authz-req+jwt` requests with pinned `kid`/public key, matching `iss`/`client_id`, audience `https://self-issued.me/v2`, `response_type=vp_token`, `response_mode=direct_post`, and a five-minute-or-shorter lifetime. This profile requires independent 43-character base64url nonce/state values. Prefix-based client identifiers, unsigned requests, request-URI fetching, redirects, external offers and alternative response modes are unsupported.

DCQL must request exactly one `dc+sd-jwt` credential of the linked-document VCT and a nonempty set of supported flat paths (`name`, `address`, `birthdate`, `gender`, `document_expiry_date`). Nested paths, filters, duplicate paths and unsupported claims fail closed. Missing requested attributes also fail closed. Consent is bound to an immutable signed request and exact credential hash. The native holder selects only requested disclosures, preserves their original bytes/order and signs a [RFC 9901](https://www.rfc-editor.org/rfc/rfc9901.html) `kb+jwt` with `aud`, `nonce`, `iat` and `sd_hash` of the exact selected SD-JWT prefix including the final `~`. The direct POST form contains `vp_token` as the DCQL query-ID-to-array JSON object and the signed state; there are no automatic retries or response redirects. A failed POST requires a fresh request. A review is consumed on approval or cancellation, and verifier/nonce reuse is rejected within the running process. The verifier must check freshness, binding and replay across process restarts. Once an approved POST has begun, leaving the screen cannot retract it.

Build with `MIKAKI_OID4VP_VERIFIERS` containing a JSON array of operator-approved registrations (maximum 32), each with `client_id` (no colon prefix except the explicit `oid4vp_final_x509_hash` profile), `name`, exact `response_uri`, `kid` and public P-256 `jwk` (`kty`, `crv`, `x`, `y`). Registrations are compiled into Rust; requests cannot install signing identities or destinations. The explicit request-key profile below permits authenticated recipient keys for that request only. The default empty registry disables presentation. Configure and qualify the real verifier separately before enabling it. The app never passes a credential or private key to the WebView; only the requested consent values are displayed and cleared on cancel, navigation or backgrounding.

The interoperable test vector is generated by `crates/identity/examples/presentation_fixture.rs` with disposable fixture keys and synthetic attributes. Independent Node JOSE checks the signed request, issuer signature, disclosed hashes, holder key, exact `sd_hash`, nonce and audience, plus omission of address/gender. Browser tests check approval, cancellation, navigation and late review responses. These are local checks rather than certification or a live third-party verifier trial.

## mdoc and ISO transport boundaries

The shared `mdoc` module issues and verifies a first-party `IssuerSigned` credential with custom doctype and namespace `app.tossa.mikaki.linked_document.1`. It uses CBOR tag-24 IssuerSignedItem bytes, independent 16-byte random values, SHA-256 ValueDigests, a tag-24 MobileSecurityObject, ES256 COSE_Sign1 IssuerAuth and `x5chain` containing the Document Signer certificate. The MSO binds the dedicated holder COSE_Key and a validity interval of at most five minutes. It is a Mikaki linked-attribute credential with the same static-data assurance described above, not `org.iso.18013.5.1.mDL`, a government PID or a statement of current driving entitlement. Its custom fields are name, address, birthdate and optional gender/document expiry. Relying parties must understand this profile and its assurance limits.

The Worker advertises `linked_document_mdoc` only when `IDENTITY_MDOC_CERT_DER` is configured as base64url DER. Its leaf public key must match the dedicated `IDENTITY_ISSUER_JWK`, cover the entire issued MSO validity interval, have digitalSignature KeyUsage (without keyCertSign), BasicConstraints CA=false and the mdoc Document Signer EKU `1.0.18013.5.1.2`. Duplicate certificate extensions fail closed. Operator validation and relying-party IACA trust, chain and revocation policy are separate: native receipt verification pins the issuer key obtained over the existing configured TLS channel and does not establish an IACA chain. Do not use the disposable certificate/key from tests in a deployment.

OID4VP Final now accepts one `mso_mdoc` DCQL query with the exact `meta.doctype_value`, namespace/element paths and optional `intent_to_retain`. It displays retention intent before approval. Selected original IssuerSignedItem bytes and original IssuerAuth are preserved. DeviceSigned contains empty DeviceNameSpacesBytes and a detached ES256 DeviceSignature over DeviceAuthenticationBytes, signed by the MSO's existing Keystore device key. The final DeviceResponse is base64url encoded and placed in the existing DCQL `vp_token` response. Receipt format, signed request, credential hash, consent and nonce consumption remain bound in native state. The encrypted Android receipt retains its format; existing SD-JWT receipts remain readable.

The preregistered OID4VP Final adapter also supports `direct_post.jwt` using **ECDH-ES / A256GCM** for both credential formats. Add `response_encryption` to a verifier registry entry with `{ "kid": "receiver-key-id", "alg": "ECDH-ES", "enc": "A256GCM", "jwk": { "kty": "EC", "crv": "P-256", "x": "...", "y": "..." } }`. This is trusted, preregistered encryption metadata: request-supplied `client_metadata`, key URLs or keys are rejected. With that policy present, the signed request must use `direct_post.jwt`; a plain `direct_post` request fails closed. Entries without an encryption policy retain the plain profile and reject encrypted requests. Unknown algorithms, enc values, empty/oversized kid and invalid/noncanonical public keys are rejected. Provision a dedicated recipient encryption key separately from the verifier request-signing key. The default verifier registry remains empty.

After one-use approval, the native adapter creates a fresh P-256 ephemeral key and 96-bit IV. The compact JWE uses RFC 7518 SHA-256 Concat KDF (AlgorithmID A256GCM, empty PartyUInfo, nonce bytes as PartyVInfo, 256-bit SuppPubInfo) and AES-GCM with the protected header as associated data. The protected header contains `alg`, `enc`, registered `kid`, public `epk` and base64url nonce `apv`; it contains no private key. The unsigned encrypted JSON contains the DCQL `vp_token` map and `state`. HTTP sends only form parameter `response`; neither `vp_token` nor `state` appears outside the JWE. All encryption/signing/transport data remains native, and existing exact HTTPS destination, no-redirect policy, credential hash, expiry, cancellation and consent consumption checks apply. Denial sends no credential; encryption failure cannot trigger plaintext fallback.

For mdoc, the Final transcript hashes CBOR `[client_id, nonce, recipientJwkThumbprint, response_uri]`, where the thumbprint is the raw SHA-256 bytes of the RFC 7638 public-key member serialization. Plain responses continue to use null in that position. The same approved-request snapshot supplies both the encryption recipient and the DeviceSignature transcript. Independent JOSE decryption and Node COSE verification cover both formats, fresh ephemeral/IV responses, wrong-key rejection, ciphertext/header nonce tampering and failure of DeviceSignature verification with a null recipient binding. This follows [OID4VP Final sections 8.3 and B.2.6](https://openid.net/specs/openid-4-verifiable-presentations-1_0-final.html#section-8.3). It is an explicitly scoped **Final** adapter; The separate Draft 18 adapter below implements a legacy wire subset; X.509 trust, DeviceMAC and full Annex A/B or 23220 qualification remain separate work.

An explicit `profile: "oid4vp_draft18_mdoc"` registry entry enables a **preregistered Draft 18 mdoc wire adapter**, with mandatory `response_encryption` ECDH-ES/A256GCM. Default/omitted `profile` is `oid4vp_final`. A registry entry selects exactly one trusted protocol; request contents cannot switch it. Native review creates a fresh 32-byte CSPRNG nonce for the Draft 18 adapter and retains it in the same immutable approved request as the consent, credential hash and requested fields. The nonce cannot come from the request/WebView and is not reused after consumed consent. Registry client IDs remain unique across profiles.

This adapter requires a signed ES256 request with the existing issuer/audience, registered kid/destination, fresh iat/exp, 43-character nonce/state rules, `client_id_scheme: "pre-registered"`, `require_signed_request_object: true` and `response_mode: "direct_post.jwt"`. It accepts one inline Presentation Definition (id bounded to 128 bytes), one input descriptor whose id is the exact custom linked-document doctype, `format.mso_mdoc.alg: ["ES256"]`, `limit_disclosure: "required"`, and up to five known fields with exactly one canonical `$['namespace']['element']` path and required Boolean retention intent. Unknown options, filters, optional claims, wildcards, alternative paths, external definition/metadata URLs, multiple descriptors and mixed DCQL/PE requests fail closed. Original request bytes, not an internal normalized query, determine the request hash. Retention intent and selected values use the existing native consent screen.

The Draft 18 transcript is `[null, null, [SHA256(CBOR([client_id, walletNonce])), SHA256(CBOR([response_uri, walletNonce])), nonce]]`. The JWE `apu` is base64url of the **UTF-8 walletNonce string** and `apv` is base64url of the UTF-8 verifier nonce; those exact bytes feed the Concat KDF and authenticated header. The encrypted JSON uses a single base64url `vp_token` string plus `state` and a Presentation Submission with a fresh id, exact definition_id, and one descriptor_map entry `{ "id": "app.tossa.mikaki.linked_document.1", "format": "mso_mdoc", "path": "$" }`. It never uses Final's DCQL response map or handover hash. Independent JOSE/CBOR/COSE tests verify decryption, selected fields, submission mapping and generated-nonce binding, including rejection of Final substitution and modified apu. This is independently implemented against [OID4VP Draft 18](https://openid.net/specs/openid-4-verifiable-presentations-1_0-18.html) and the [18013-7:2024 Annex B wire descriptions hosted by France Identité](https://playground.france-identite.gouv.fr/doc/assets/iso18013.pdf), with `civ` consulted for PE parsing boundaries rather than its older transcript constructor.

This preregistered subset is **not Annex B conformance**, nor a claim that the 2024 wire descriptions qualify the entire 2025 edition. Dynamic X.509 client identifiers and reader certificate status, signed dynamic client metadata, verifier response-code redemption/session binding, DeviceMAC, deployed-reader interoperability and formal 2025/23220 qualification remain separate work. Do not advertise the Annex B static wallet metadata or treat pasted diagnostic requests as a qualified same-device invocation. The existing registry still defaults to empty.

The Android native deep-link handler accepts bounded same-device **GET request_uri**, plus opt-in `oid4vp_final_x509_hash` POST as described above. Configure `MIKAKI_OID4VP_REQUEST_URIS` at build time alongside `MIKAKI_OID4VP_VERIFIERS`, for example `[ { "client_id": "registered-verifier", "request_uri": "https://verifier.example/requests" } ]`. Each client has one exact HTTPS endpoint without query, fragment or user credentials. Invocations may add a bounded query to that exact endpoint for an opaque session identifier; the scheme, host, port and path must still match. The client must also exist in the signing registry. Final uses `openid4vp://?client_id=...&request_uri=...`; Draft 18 uses `mdoc-openid4vp://?client_id=...&request_uri=...`. Both parameter values must be URL-encoded. The `oid4vp_final_x509_hash` profile additionally accepts one `request_uri_method=get` or `request_uri_method=post` parameter. Duplicate or other outer parameters, inline objects, POST for older profiles, fragments and cross-profile schemes are rejected.

The request is queued in Rust for at most 120 seconds, including cold start; the presentation commands expose only a one-use opaque invocation ID, and the bundled UI does not read or fetch the raw URL. The existing Tauri deep-link plugin also broadcasts its standard raw URL event; this subset does not isolate that plugin event from other WebView listeners. Retrieval uses a native HTTPS GET, a 20-second timeout, no redirects and a maximum 16 KiB `application/oauth-authz-req+jwt` response. The fetched signed request must match the invocation's client ID and pass the existing registered key, destination, profile, clock, nonce and field-policy checks before any attributes are returned. It then enters the same explicit approval screen and encrypted response path as manual review. New invocations invalidate older native consent; navigation/cancellation during retrieval rejects late consent. No automatic credential transmission occurs. This is a preregistered same-device invocation subset; the transport itself does not authenticate a reader certificate (the opt-in certificate_trust policy below does) or complete Annex B qualification. Both registries default to empty.

After a successful direct_post or direct_post.jwt submission, the native wallet reads a bounded acknowledgement following [OID4VP Final section 8.2](https://openid.net/specs/openid-4-verifiable-presentations-1_0-final.html#section-8.2). HTTP 200, application/json and an object of at most 8 KiB are required. Unknown extension members are ignored; duplicate, null or non-string redirect_uri values are rejected. An absent redirect_uri requires no browser action. No HTTP redirect is followed.

To allow browser completion, configure `MIKAKI_OID4VP_REDIRECT_URIS` at build time, for example `[ { "client_id": "registered-verifier", "redirect_uri": "https://verifier.example/complete" } ]`. This separate registry defaults to empty. Each selected client must have one HTTPS endpoint with no credentials, query or fragment. The returned redirect_uri must match its exact scheme, host, port and path and carry only one `response_code` either in the query or fragment, never both. The opaque code is bounded to 22–128 ASCII URL-safe characters; freshness, cryptographic entropy, one-use redemption and binding to the verifier's browser session are responsibilities of the verifier and cannot be inferred from its string. This is an explicit subset: custom schemes, random path components, arbitrary query parameters and additional callback destinations are unsupported.

Only the native opener receives the validated completion URL and code. The WebView receives an outcome, never the code. The already consumed approval cannot resubmit credentials to retry completion. Cancellation or a replacement invocation before browser dispatch prevents a late acknowledgement from opening the old URL. After successful HTTP submission, an invalid acknowledgement, unregistered callback or unavailable browser returns a sent-credential outcome with a separate completion failure; the UI makes clear that attributes were already sent and does not retry. Opening the browser means dispatch to the registered endpoint, not proof that the verifier has redeemed the response_code or completed authentication. Rust tests cover malformed bodies, status/media/size limits, endpoint and code restrictions and generation cancellation; UI tests cover opened/rejected/unavailable/invalid outcomes and navigation during submission. Actual browser session redemption and reader interoperability remain unqualified.

The online and proximity registries can now opt into **registered reader certificate-chain authentication** by adding `certificate_trust: { "trust_anchors": ["standard-padded-base64-DER-CA"], "dns_name": "verifier.example" }`. Proximity may omit dns_name; online registrations require it. The registered public key remains required, so a CA-issued replacement key does not silently gain authorization. The default registries remain empty, and an existing entry without certificate_trust keeps its documented key-pinned profile. A certificate-required entry cannot fall back to a request without a valid chain. Provision the CA material out of band; a certificate supplied in a JOSE/COSE header never becomes a trust anchor.

The shared validator uses rustls-webpki path validation with a small p256 signature provider, without system TLS roots, AIA fetching or C-library/platform crypto requirements. It supports P-256/SHA-256 certificate signatures, up to four supplied DER certificates of at most 4 KiB each, and up to eight distinct configured CA anchors. It checks issuer signatures, validity (including configured anchors), CA/basic/key-usage restrictions, intermediate path-length and name constraints, duplicate and unsupported critical extensions, and the exact registered leaf public key. Leaf certificates must have critical digitalSignature KeyUsage, critical non-CA BasicConstraints and critical readerAuthentication EKU `1.0.18013.5.1.6`. CA EKU, when present, must permit that reader purpose. If dns_name is configured, it must be a lowercase ASCII DNS name and match an explicit DNS SAN; IP addresses, CN fallback and wildcard matching do not establish the registered name. Certificate subjects do not replace the operator-assigned consent display name or expand the supported attributes.

Signed online requests use a standard-base64 x5c header chain (leaf first). Proximity ReaderAuthentication accepts COSE x5chain label 33 as a leaf certificate or a leaf-first array when the entry requires CA validation. It validates the certificate chain and registered key before verifying the ReaderAuthentication signature over the original transcript and ItemsRequest. Independent Node X509/JOSE and encrypted reader tests exercise these paths; Rust tests cover unknown roots, certificate/signature tampering, missing/interchanged chains, expired/future certificates, CA and EKU restrictions, name constraints, wildcard/name failures, excessive depth/size and duplicate extensions. The shared crate also builds for wasm without enabling a ring backend.

This is an explicit **preregistered reader-PKI subset**, with reader EKU as a local trust policy. It is not support for OID4VP's x509_san_dns/x509_hash client identifier schemes or dynamic client_metadata (which have separate rules in [OID4VP Final section 5.9](https://openid.net/specs/openid-4-verifiable-presentations-1_0-final.html#section-5.9)). The optional offline CRL policy below adds bounded revocation checks; chain validation without that policy does not assert that a certificate is currently unrevoked. It does not change government-card signature trust or qualify an IACA/DocumentSigner chain for issued mdocs. Dynamic reader onboarding, online OCSP/CDP retrieval, deployed trust lists and full ISO qualification remain separate work.

To require offline revocation checks, add `revocation: { "crls": ["standard-padded-base64-DER-intermediate-CRL", "standard-padded-base64-DER-root-CRL"], "max_age_seconds": 86400 }` inside `certificate_trust`. Provision and refresh the CRLs out of band together with the CA registry. The validator requires complete, direct v2 CRLs signed with ECDSA/SHA-256, with AuthorityKeyIdentifier, CRLNumber and nextUpdate, following the relevant [RFC 5280 CRL fields](https://www.rfc-editor.org/rfc/rfc5280#section-5). It checks the leaf and every intermediate against the actual path issuer, verifies CRL signatures and cRLSign usage, and rejects revoked certificates or missing issuer status. A configured policy cannot fall back to chain-only validation. Trust anchors themselves are managed by removing them from the configured registry.

The policy accepts 1–8 CRLs, at most 32 KiB DER each and 128 KiB total, with one CRL per issuer and at most 1,024 revoked entries per CRL. max_age_seconds must be 60–604800. A CRL must satisfy thisUpdate ≤ current time < nextUpdate and current time < thisUpdate + max_age_seconds; expired, future-dated and stale CRLs produce distinct failures. Delta and indirect CRLs, removeFromCRL entries, unsupported critical extensions and ambiguous duplicate issuer CRLs are rejected. No certificate-provided distribution URL is fetched and OCSP is unsupported. A recent configured CRL represents that issuer's published snapshot, not a live query or proof that no later revocation exists.

Online approval and proximity session deadlines are bounded by certificate validity and CRL freshness, with another deadline check before response submission/encryption. Consent cannot remain usable after that bound. Android receives the immutable approval deadline for near-field transfers and maps it against the wall/monotonic clock pair captured at session creation. The first response, every BLE notification continuation and every NFC GET RESPONSE are checked, with a matching timer to close stalled transfers. Clock rollback cannot extend the original two-minute session or the mapped certificate/CRL deadline. Expiration discards unsent ciphertext and rejects further response fragments. A fragment already handed to the OS or reader cannot be retracted; interruption does not establish that no bytes were sent, or that the reader accepted a credential. NFC tests exercise expiry before the first response and during fragmented retrieval. Rust and independent OpenSSL tests cover whole-chain clean/revoked status, and an independently implemented encrypted reader exercises clean, revoked, stale and missing-CRL cases. Registrations without revocation retain the explicit chain-only profile.

The Android near-field implementation uses QR engagement and BLE peripheral/server mode over GATT. It generates a fresh P-256 ECDH key and UUID for each session, advertises no device name, accepts one reader connection and one encrypted SessionEstablishment, and closes on cancellation, backgrounding, timeout or invalid input. Session keys use HKDF-SHA-256 with the hash of **tag-24 SessionTranscriptBytes** as salt and separate SKReader/SKDevice labels; AES-256-GCM uses separate direction fields and counters starting at one. Ciphertext replay or failed authentication terminates the session, without retry. Fragmentation is bounded to 32 KB, the session lasts at most 120 seconds and never outlives the credential. It also supports an explicitly selected NFC static handover via Android HCE, followed by BLE peripheral retrieval. It also supports TNEP negotiated NFC handover to BLE, as described below. It does not implement BLE central/client mode, L2CAP or multi-document exchanges.

NFC static handover uses a read-only NFC Forum Type 4 NDEF tag in an Android `HostApduService`: select the NDEF AID, select the capability container or NDEF file, then bounded short-APDU READ BINARY. It publishes only the fresh engagement and BLE carrier in a Handover Select 1.5 NDEF message. The BLE service UUID is little-endian in the OOB carrier; DeviceEngagement omits QR retrieval methods. The exact emitted Handover Select bytes and null Handover Request form the NFC SessionTranscript handover. NFC and QR are explicit native profiles: no transcript inference or fallback is accepted. The HCE service requires the OS-only BIND_NFC_SERVICE permission and an unlocked device; it is armed only while this app's explicit native session is active, requests foreground service preference and clears engagement on BLE handshake, cancellation, backgrounding or the 120-second deadline. Cold process restarts expose no NDEF. NFC field removal resets file selection but keeps the BLE flow alive so the user can move the phone away and approve. UPDATE BINARY, extended APDUs, invalid offsets/lengths and writes fail closed. HCE/foreground routing follows [Android's HCE documentation](https://developer.android.com/develop/connectivity/nfc/hce); NDEF/static handover was checked against [Multipaz's engagement implementation](https://github.com/openwallet-foundation/multipaz/blob/main/multipaz/src/commonMain/kotlin/org/multipaz/mdoc/nfc/MdocNfcEngagementHelper.kt). This static NDEF path provides NFC engagement followed by BLE retrieval.

A third explicit profile, `qr_nfc`, advertises **only NFC data retrieval** in the QR DeviceEngagement: method type/version `[1, 1]`, maximum command data 255 bytes and response data 256 bytes. No Bluetooth operation or permission request occurs in this mode. After scanning the QR, the reader selects mdoc data AID `A0000002480400`; short ENVELOPE (`INS C3`) commands chain DO53-wrapped encrypted SessionEstablishment with CLA `10` and no Le except the final command (CLA `00`, required Le). The service returns null for that final APDU, allowing the native verification/consent flow to run without blocking Android's HCE handler. Only an approved, immutable request can supply encrypted SessionData for the deferred response. Remaining DO53 bytes are returned through bounded GET RESPONSE (`INS C0`), respecting each Le and using `61xx`/`6100` until final `9000`. The send command resolves only when the last response fragment has been returned, not when a relying party has accepted the credential. DO53 requires canonical definite lengths; data is capped at 32 KB, commands at 255 data bytes and the session at 120 seconds. Empty/trailing/nonminimal DO53, malformed APDUs, unsupported extended lengths, premature GET RESPONSE, duplicate request/response and reselection fail closed. This narrow short-APDU profile is advertised explicitly so a reader can obey the limits. The [Multipaz NFC transport](https://github.com/openwallet-foundation/multipaz/blob/main/multipaz-android-legacy/src/main/java/com/android/identity/android/mdoc/transport/DataTransportNfc.kt) was used to review the wire protocol, not copied as implementation.

For `qr_nfc`, keep the phone in the reader's NFC field while checking attributes and approving; field loss/deselection, cancellation, backgrounding and timeout destroy the native transport and pending cipher state. A Rust-only transport-close watcher invalidates the matching session generation, drops any stored pending flow/cipher keys and emits an ID-only UI event to clear the consent display. Old close notifications cannot cancel a replacement session. A fresh engagement is required after failure. DeviceSignature and session keys bind the original NFC-only **QR** engagement; NFC static-handover or BLE QR transcripts cannot be substituted. Reader authentication, registered key/certificate purpose, credential hash, one-use native review and selected-field/retention consent are identical to the BLE paths. Physical HCE deferred-response latency, reader transceive timeout/WTX behavior and long fragmented transfers remain unqualified and require a separately implemented reader with an appropriate consent timeout. This is not a claim of full ISO 18013-5 certification.

The fourth explicit profile, `nfc_negotiated`, uses TNEP single-response Connection Handover 1.5 before BLE peripheral retrieval. The initial public NDEF advertises `urn:nfc:sn:handover` (TNEP 1.0, WT_INT 32, N_WAIT 15, maximum NDEF 4094 bytes). The Type 4 capability container allows short UPDATE BINARY only for this profile, advertising MLc 255 and MLe 256 bytes. Service selection uses a single short well-known `Ts` record for that exact URI, returning `Te` status zero. Writes support one-shot NLEN+message or a zero-NLEN reset, contiguous fragments at offset 2 onward and an exact final NLEN; duplicate resets, gaps, overlaps, mismatched length and writes after handover are terminal. During Rust validation the NDEF file reports zero length so the poller uses TNEP waiting; no HCE thread blocks on native verification.

Rust accepts a bounded Hr 1.5 message, validates NDEF message flags, record lengths/unique IDs, alternative-carrier references and auxiliary references, and selects a referenced, active/activating BLE OOB offer compatible with the mdoc peripheral. Unsupported-only offers and missing/malformed/duplicate roles fail closed. Short and long NDEF payload encodings are accepted for Hr; chunked NDEF is excluded. The holder chooses its fresh service UUID and publishes Hs only after Rust has accepted the original Hr. BLE session establishment before this publication is rejected. Exact received **Hr** and emitted **Hs**, without decode/re-encode normalization, form the NFC transcript `[Hs, Hr]`; HKDF, ReaderAuthentication and DeviceSignature use that same transcript. A missing negotiation or QR/static `[Hs, null]` substitution cannot establish the session. Handover messages remain native and contain no identity attributes. Field loss before Hs publication, backgrounding, cancellation, validation errors and the 120-second transport deadline terminate the matching native flow; after Hs publication the reader can use BLE outside the NFC field. The [NFC Forum Connection Handover description](https://nfc-forum.org/build/specifications/connection-handover-technical-specification/) and [Multipaz NFC engagement implementation](https://github.com/openwallet-foundation/multipaz/blob/main/multipaz/src/commonMain/kotlin/org/multipaz/mdoc/nfc/MdocNfcEngagementHelper.kt) informed this independently implemented profile. Physical TNEP polling latency and reader interoperability remain unqualified; central-mode and other carriers are separate work.

A fifth explicit profile, `nfc_negotiated_data`, completes **NFC engagement and NFC encrypted retrieval without QR or Bluetooth**. It reuses the TNEP writable Type 4 flow, but Rust accepts a referenced active/activating external carrier `iso.org:18013:nfc` (carrier version 1) instead of a BLE offer. Command/response capacity TLVs must occur once, in order, be bounded unsigned integers and contain no trailing data; capacities below 255 command bytes or 256 response bytes are rejected. Larger reader capacities are accepted, but the selected Hs advertises only the holder's supported 255/256 short-APDU limits. The Hs alternative-carrier record references carrier ID `nfc` and auxiliary ID `mdoc`, and its DeviceEngagement omits QR retrieval methods. NFC-only and BLE-only negotiation are selected by the user through separate native profiles, with no automatic transport or transcript fallback.

After Rust accepts the exact Hr, Hs remains readable through NDEF while the NFC data protocol waits for `A0000002480400` selection. Only that exact short SELECT (optional Le zero) switches APDU routing to the one-use encrypted data protocol; later NDEF reads or reselection cannot return to engagement. ENVELOPE/DO53, deferred native verification/consent, response fragmentation and the 120-second deadline follow the existing NFC data path. Exact **NFC** Hr/Hs bytes bind session encryption, ReaderAuthentication and DeviceSignature, so BLE negotiation, QR and static transcripts cannot be substituted. Keep the phone in the field during attribute review and approval; field loss before data selection or during transfer cancels the matching flow and clears pending consent/key state. This mode never opens GATT, advertises Bluetooth or requests Bluetooth permissions. Independent Node cryptography checks cover the selected carrier/limits, signed selective response and profile substitution; pure JVM routing tests cover Hs reads before data selection and prohibit return to NDEF. Physical HCE/TNEP/APDU timeout and independent-reader interoperability remain unqualified. NFC carrier encoding was checked against [Multipaz's NFC connection method](https://github.com/openwallet-foundation/multipaz/blob/main/multipaz/src/commonMain/kotlin/org/multipaz/mdoc/connectionmethod/MdocConnectionMethodNfc.kt); this is an independently implemented narrow holder profile, not full ISO certification.

Enable the reader profile at build time using `MIKAKI_MDOC_READERS`, a JSON array of `{ "name": "operator-approved reader", "jwk": { "kty": "EC", "crv": "P-256", "x": "...", "y": "..." } }`. It defaults to `[]`, which disables proximity before Bluetooth advertising. This registry is separate from the OID4VP verifier registry. The first profile requires one signed DocRequest for the custom linked-document doctype/namespace, using detached ES256 ReaderAuthentication and a single DER leaf certificate in x5chain. The leaf must be in its validity interval, match exactly one explicitly pinned reader public key, have digitalSignature KeyUsage and mdlReaderAuth EKU `1.0.18013.5.1.6` (both critical), CA=false, no keyCertSign, no duplicate extensions and no unsupported critical extensions. The reader name comes from the registry. This is explicit key pinning, not Reader CA chain or revocation validation. EKU checked against the [European Commission reader-auth profile implementation](https://github.com/eu-digital-identity-wallet/eudi-lib-android-iso18013-data-transfer/blob/main/transfer-manager/src/main/java/eu/europa/ec/eudi/iso18013/transfer/readerauth/profile/KeyExtended.kt); transport and session-key details were checked against [Multipaz](https://github.com/openwallet-foundation/multipaz).

The diagnostics screen selects QR or NFC engagement and shows a public QR or tap instructions, then the authenticated reader name, requested values and retention intent. Attributes are sent only after explicit approval; the immutable request, credential hash, native consent ID and session ID are bound. The signing key remains the MSO device key in Keystore; ephemeral ECDH/session keys, raw requests, encrypted transport packets and credentials do not cross the WebView boundary. Cancelling while permission/start/receive/sign/send is pending invalidates native state and clears displayed values; late callbacks cannot restore consent. Android 12+ requests BLUETOOTH_ADVERTISE and BLUETOOTH_CONNECT only when starting this feature; no scan or location permission is requested. Physical qualification with a separately implemented reader remains required. Never replace the ephemeral session key with the long-lived MSO signing key. `madowi-mdoc` supplies useful reader-side structures and transport lessons, not a complete holder to transplant. Its key derivation and civ's older OID4VP transcript builders require independent review rather than being treated as normative specifications. Final and ISO profiles must be chosen by an explicit trusted adapter; a request must not silently select a different transcript.

Independent Node CBOR/crypto checks verify certificate/public-key equality, COSE signatures, original item digests, omitted unrequested fields and the exact Final DeviceAuthentication transcript. Actual workerd tests issue both formats from both card types using one-use consent/proof grants. The public fixture certificate uses the known disposable `[4; 32]` key, expires in 2036, and is not a trust anchor. Physical-device persistence, real issuer PKI and third-party wallet/reader presentation interoperability remain unqualified; the Multipaz host SDK issuance check is described above.
