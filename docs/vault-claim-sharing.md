# Historical format-1 Vault attribute sharing for UserInfo

**Retired:** this document records the former `/vault/attributes` ciphertext share and claim-release design. Format-1 storage, share/release routes and Owner UI were removed for the fresh `0001_owner_vault_initial.sql` baseline. Historical deployment statements below refer to the old database and do not describe current product availability. The current [Owner record-v2 name-sharing panel](vault-owner-name-sharing.md) connects one saved name to separate system and RP approvals; production sharing policies remain disabled. See [Agent OAuth](agent-oauth.md) for exact-source v2 grant behavior.

The owner-only Vault is implemented. An owner-approved UserInfo system recipient path and a separate RP consent ledger are implemented behind disabled D1 policies. The local Worker now accepts `openid profile`, binds that scope to the issued code/token, and conditionally releases `name` through the dedicated claim Worker after current RP consent and Grant checks. A disposable local Secrets Store secret has been used to qualify the actual Vault screen, both real Workers and a reference RP through authorization, token exchange and UserInfo. SSO and the saved ciphertext are fixtures; an intended passkey device, named RP application and production `name` release have not been qualified. The policies default to disabled. Ordinary `openid` login works without Vault creation/unlock.

The [protocol review](vault-protocol-review.md) keeps this ordinary profile-release path separate from credential presentation. OpenID4VP is a candidate when a relying verifier needs issuer-backed evidence; it does not turn a self-entered `name` into verified identity or supply Vault write authority. OID4VP adoption does not automatically enable or supersede the disabled UserInfo path.

Later local source adds [same-account passkey registration and saved-name transfer](vault-passkey-transfer.md) without changing the V1 envelope. It replaces the saved revision and invalidates old shares; the historical owner-only baseline below predates that slice. Backup/all-key-loss recovery and real-device continuity remain unverified.

## Implemented owner only path

The Rust Worker provides authenticated `GET`, `PUT`, and `DELETE /vault/attributes/{attribute}`, and `/vault` provides the `name` encryption/unlock UI. The latter requires SSO and a PRF capable passkey. Passkey registration requests the PRF extension but does not require support for ordinary login. Credentials created before this request may lack PRF support; same-account additional Passkey and saved-name/note transfer now have [local evidence](vault-passkey-transfer.md), but they are not recorded as deployed and all-key-loss recovery remains unavailable. Migration `0002_vault_attribute_storage.sql` creates the D1 head, retry records, and GC cursor. A Worker without an R2 binding returns 404 for Vault. Authorization currently uses a local owner policy shaped like an AuthZEN subject/action/resource decision; an external HTTP PDP and Grant lookup are not implemented.

The subject is a verified AccountId of type `mikaki-account`; the resource is `mikaki-vault-attribute` with ID `vault-attribute:<owner>:<attribute>`. Allowed owner actions are `vault.attribute.read-ciphertext`, `vault.attribute.read-owner-envelope`, `vault.attribute.write`, `vault.attribute.delete`, `vault.attribute.share-system`, and `vault.attribute.revoke-system`. Unknown actions and service principals are denied. This uses the [AuthZEN 1.0](https://openid.net/specs/authorization-api-1_0.html) information model, not demonstrated external PDP interoperability.

An attribute name has 1–64 lowercase ASCII letters, digits, hyphen, or underscore. PUT accepts version 1 base64url ciphertext (up to 24 KiB) and owner envelope (up to 8 KiB). R2 stores immutable ciphertext at a random key; D1 stores its digest, head, revision, and owner envelope. GET verifies the stored blob digest. The server cannot verify client decryptability.

The browser creates a random 32 byte data key per attribute/revision and encrypts content with AES-256-GCM. Ciphertext bytes are `0x01 | nonce(12) | ciphertext+tag`. It derives an AES-256-GCM wrapping key from WebAuthn PRF output with HKDF-SHA-256. The owner envelope contains version, credential ID length and ID, 32 byte PRF input, 32 byte salt, 12 byte wrap nonce, and 48 byte wrapped data key. HKDF context binds origin, attribute, and credential; both AEAD AADs bind origin, attribute, and revision. PRF output and data key never go to the server. A different origin, lost passkey, or PRF incapable passkey cannot directly decrypt; rewrapping and recovery are still missing.

Creation requires `If-None-Match: *`; update/delete require `If-Match: "<revision>"`. Writes require same origin `Origin` and a 43 character `X-Operation-ID`. The same ID and request are idempotent; a different request with the same ID returns 409. Recheck revision, quota, SSO, credential, and account at conditional D1 commit. Deletion is a versioned tombstone. Limits: 32 attribute IDs per account and 20 writes per rolling 60 seconds. Daily GC removes unreferenced R2 blobs older than 24 hours; retry records are gradually removed after 90 days. D1/R2 cannot commit atomically, so orphaned blobs may remain until GC.

## System recipient sharing (disabled by default)

A user supplied `name` remains a Vault attribute, not mandatory account registration data or a verified legal name. The unlocked device can wrap only that attribute's data key for a dedicated UserInfo system principal, in addition to the owner's envelope. That principal could decrypt the shared attribute by itself; call this explicitly server readable for that purpose. Never wrap a Vault root/collection key or reuse an OIDC signing key.

Migration `0008_vault_attribute_sharing.sql` adds a recipient envelope, versioned system Grant, immutable share audit, and D1 policy. It was applied in production on 2026-09-24 with sharing disabled and a seven-day Grant TTL. The owner can approve sharing of the saved `name` after PRF unlock only when an operator enables the policy. The browser checks recipient-key continuity, unwraps the existing data key, creates the ML-KEM envelope, and clears the data key. The OP Worker checks SSO, same origin, attribute revision and ciphertext digest, active recipient key and directory revision, policy revision, and operation ID. Before the D1 write, it asks the claim Worker over a service binding to open the envelope with its Secrets Store seed and validate the exact stored ciphertext. Only a success status crosses back; no data key or plaintext does. An atomic D1 batch then stores the envelope, Grant, and audit. A stale revision or changed key fails closed. Revocation is an owner action; a Vault update or policy change revokes an active Grant. The former local Rust, workerd and Chromium UI paths were exercised before retirement; their format-1 happy-path suite has been removed. A synthetic product envelope was verified with the live seed without recording a Grant. The full production owner flow and recovery remain activation gates.

Migration `0010_vault_claim_release.sql` adds a disabled RP release policy and per-account, per-client `name` consent records. A release binds the current attribute revision, system Grant version, client revision, and app connection Grant version, and has its own version, expiry, and immutable audit. An owner can grant or revoke it from Vault with an active passkey SSO session. D1 triggers reject a grant without current sharing, an active private-key client, and an active app connection; changing the system Grant, RP registration, app connection, policy, or account state revokes active releases. The Vault UI lists only already-connected RPs. A system Grant alone does not authorize any RP to receive `name`. AuthZEN makes an access decision; it is not key material or the consent ledger. A normal OIDC access token gives no Vault permission.

The first local release path adds migration `0023`: a code's scope is immutable; the token response carries `profile` when requested; UserInfo requires the live token, scope and RP-specific ClaimRelease. The claim Worker fetches only the current blob, checks its digest, Grant, consent, client/connection revisions and recipient key, decrypts under the issuer/account/attribute/revision binding and conditionally audits before returning `name`. Missing consent omits the claim; a missing recipient secret, damaged blob or failed audit makes the profile request fail closed. `name` enters Discovery's `claims_supported` only when the disabled share and release policies are both enabled and the bindings exist. Keep both policies disabled until a named RP, intended device and operational controls are qualified.

The [recipient key and envelope format candidate](vault-recipient-envelope-format.md) specifies byte-level identity, suite, context binding, and the interoperability gates for `AttributeRecipientEnvelope`. Its frame is accepted by the disabled system-sharing path, but no production envelope has been written.

An attribute update revokes the old system Grant. A new revision requires the owner to share again; an absent matching envelope must stop UserInfo release rather than reuse an old one. Future RP release must check both the system Grant and a live RP-specific ClaimRelease. For future cryptographic separation, reencrypt with a fresh data key for remaining recipients. Already released plaintext/key copies cannot be recalled.

Disabling a recipient key revokes its active Grants through migration `0009`, while retaining envelope and audit history. A replacement key needs a new owner-produced envelope and Grant; it cannot make the old frame usable again.

For an RP request, confirm the requested claim, client, and explicit RP specific release consent. The claim service receives verified account/client/attribute/revision/purpose, checks the PDP and current Grant, then unwraps only that attribute. Separately check `oidc.claim.release` and ClaimRelease. Return pairwise `sub` plus authorized claims in UserInfo, not the ID Token by default. Missing attribute/consent or PDP/key/storage outage must not produce a stale cached value; choose omission versus temporary error under a defined HTTP contract. Do not add `name` to Discovery until this entire path is implemented and tested.

The local claim Worker regression covers no-release omission, live consent reaching the fail-closed secret boundary, revocation omission and malformed requests; Rust tests cover exact origin/revision/key decryption. A separate workerd test creates a disposable local Secrets Store secret, loads a saved owner ciphertext and the actual Vault screen, and connects both real Rust Workers. The browser unlocks with a test PRF, creates the recipient envelope and system Grant, grants RP-specific release and later withdraws it. Before sharing and after sharing without RP consent, UserInfo returns only `sub`. A reference RP requests `openid profile`, exchanges an actual authorization code, validates its ID Token, verifies Discovery issuer and UserInfo subject, and receives `name` with a disclosure audit. A second login after withdrawal receives only `sub`. Reapproval restores `name`; saving a new Vault revision revokes both old Grants, and only a fresh share and RP approval releases the new value. Changing the RP registration revision revokes its release; the old token loses `name`, while a new RP key revision, browser approval and code exchange restore release. A missing current R2 blob, a thrown Claim Worker transport error and a claim-service 503 all make OP UserInfo return 503 without another audit; recovery rechecks live consent. Removing the D1 session-authority view gives a 503 without disclosure and restores on view repair. Deleting the disposable local Secrets Store key also gives a 503 without disclosure while consent and Grant stay active. These UserInfo failures carry `Retry-After: 5`, `Cache-Control: no-store`, and no token challenge. When the OP-to-Claim-Worker request is held before claim processing, a browser withdrawal causes the resumed request to return only `sub`. The same test takes a valid pre-decrypt authority snapshot, withdraws consent through the Vault screen, then executes the claim Worker's shared conditional-audit SQL: it inserts no disclosure. A separate conformance-only Worker build also pauses the real Worker after decryption; browser withdrawal makes its resumed UserInfo request fail closed with no audit. The production build excludes this pause binding. Disabling the recipient key then revokes both Grants, removes its directory entry, and stops further disclosure even on a new RP login. A changed blob digest and failed audit insert both deny release without another audit. A name-using RP application, intended passkey device and real-service D1/Secrets Store outage, latency and recovery evidence remain open. The existing Helpdesk RP has no `name`-dependent feature and is not treated as a profile consumer. Audit principal, attribute, purpose, client, versions, decision, and result without plaintext or key bytes. FileNode/JMAP uses a separate API/data model even if blob, quota, and audit infrastructure are shared. An optional `name` conformance warning alone does not mandate collecting or sharing it. [Identity Assurance](identity-assurance-adoption.md) remains a separate verified-claims gate.

The [local timeout review](userinfo-timeout-review.md) shows that aborting a service-binding fetch did not stop downstream work in Miniflare. A hard response deadline needs a cancellation or audit-outcome contract; the current 503 failure mapping does not by itself bound latency.
