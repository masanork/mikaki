# Vault attribute sharing for UserInfo

This distinguishes an implemented owner only storage path from a proposed system recipient and UserInfo claim path. A `name` claim in Discovery or UserInfo is not implemented. Ordinary `openid` login works without Vault creation/unlock.

## Implemented owner only path

The Rust Worker provides authenticated `GET`, `PUT`, and `DELETE /vault/attributes/{attribute}`, and `/vault` provides the `name` encryption/unlock UI. The latter requires SSO and a PRF capable passkey. Migration `0002_vault_attribute_storage.sql` creates the D1 head, retry records, and GC cursor. A Worker without an R2 binding returns 404 for Vault. Authorization currently uses a local owner policy shaped like an AuthZEN subject/action/resource decision; an external HTTP PDP and Grant lookup are not implemented.

The subject is a verified AccountId of type `mikaki-account`; the resource is `mikaki-vault-attribute` with ID `vault-attribute:<owner>:<attribute>`. Allowed actions are `vault.attribute.read-ciphertext`, `vault.attribute.read-owner-envelope`, `vault.attribute.write`, and `vault.attribute.delete`. Unknown actions and service principals are denied. This uses the [AuthZEN 1.0](https://openid.net/specs/authorization-api-1_0.html) information model, not demonstrated external PDP interoperability.

An attribute name has 1–64 lowercase ASCII letters, digits, hyphen, or underscore. PUT accepts version 1 base64url ciphertext (up to 24 KiB) and owner envelope (up to 8 KiB). R2 stores immutable ciphertext at a random key; D1 stores its digest, head, revision, and owner envelope. GET verifies the stored blob digest. The server cannot verify client decryptability.

The browser creates a random 32 byte data key per attribute/revision and encrypts content with AES-256-GCM. Ciphertext bytes are `0x01 | nonce(12) | ciphertext+tag`. It derives an AES-256-GCM wrapping key from WebAuthn PRF output with HKDF-SHA-256. The owner envelope contains version, credential ID length and ID, 32 byte PRF input, 32 byte salt, 12 byte wrap nonce, and 48 byte wrapped data key. HKDF context binds origin, attribute, and credential; both AEAD AADs bind origin, attribute, and revision. PRF output and data key never go to the server. A different origin, lost passkey, or PRF incapable passkey cannot directly decrypt; rewrapping and recovery are still missing.

Creation requires `If-None-Match: *`; update/delete require `If-Match: "<revision>"`. Writes require same origin `Origin` and a 43 character `X-Operation-ID`. The same ID and request are idempotent; a different request with the same ID returns 409. Recheck revision, quota, SSO, credential, and account at conditional D1 commit. Deletion is a versioned tombstone. Limits: 32 attribute IDs per account and 20 writes per rolling 60 seconds. Daily GC removes unreferenced R2 blobs older than 24 hours; retry records are gradually removed after 90 days. D1/R2 cannot commit atomically, so orphaned blobs may remain until GC.

## Proposed selective disclosure

A user supplied `name` remains a Vault attribute, not mandatory account registration data or a verified legal name. To disclose it, the unlocked device would wrap only that attribute's data key for a dedicated UserInfo system principal, in addition to the owner's envelope. That principal could decrypt the shared attribute by itself; call this explicitly server readable for that purpose. Never wrap a Vault root/collection key or reuse an OIDC signing key.

Three distinct records are proposed: `AttributeRecipientEnvelope` binds account, attribute, ciphertext revision, recipient service/key, purpose, suite, and wrapped data key; `AttributeGrant` binds recipient, operation, purpose, expiry, status, and monotonic version; `ClaimRelease` binds RP client, claim, consent version, expiry, and status. AuthZEN makes an access decision; it is not the key material or consent ledger. A normal OIDC access token gives no Vault permission.

The [recipient key and envelope format candidate](vault-recipient-envelope-format.md) specifies byte-level identity, suite, context binding, and the interoperability gates for `AttributeRecipientEnvelope`. Its probe frame is not yet a product storage format.

First sharing must authenticate the service key and its continuity on the client, then publish matching envelope, Grant, and audit atomically in D1. An attribute update must publish matching new owner/system envelopes; an absent system envelope stops UserInfo release rather than reusing an old one. Revocation first disables Grant and ClaimRelease; future reads, unwraps, and claim issuance stop. For future cryptographic separation, reencrypt with a fresh data key for remaining recipients. Already released plaintext/key copies cannot be recalled.

For an RP request, confirm the requested claim, client, and explicit RP specific release consent. The claim service receives verified account/client/attribute/revision/purpose, checks the PDP and current Grant, then unwraps only that attribute. Separately check `oidc.claim.release` and ClaimRelease. Return pairwise `sub` plus authorized claims in UserInfo, not the ID Token by default. Missing attribute/consent or PDP/key/storage outage must not produce a stale cached value; choose omission versus temporary error under a defined HTTP contract. Do not add `name` to Discovery until this entire path is implemented and tested.

Test envelope swapping across attribute, revision, service key, and purpose; concurrent revocation; absent RP consent; PDP failure; and conflicting operation ID reuse. Audit principal, attribute, purpose, client, versions, decision, and result without plaintext or key bytes. FileNode/JMAP uses a separate API/data model even if blob, quota, and audit infrastructure are shared. An optional `name` conformance warning alone does not mandate collecting or sharing it.
