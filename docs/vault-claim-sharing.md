# Vault attribute sharing for UserInfo

The owner-only Vault is implemented. An owner-approved UserInfo system recipient path and a separate RP consent ledger are implemented behind disabled D1 policies. A `name` claim in Discovery or UserInfo is not available. Ordinary `openid` login works without Vault creation/unlock.

## Implemented owner only path

The Rust Worker provides authenticated `GET`, `PUT`, and `DELETE /vault/attributes/{attribute}`, and `/vault` provides the `name` encryption/unlock UI. The latter requires SSO and a PRF capable passkey. Passkey registration requests the PRF extension but does not require support for ordinary login. Credentials created before this request may lack PRF support; there is no same-account replacement or recovery path yet. Migration `0002_vault_attribute_storage.sql` creates the D1 head, retry records, and GC cursor. A Worker without an R2 binding returns 404 for Vault. Authorization currently uses a local owner policy shaped like an AuthZEN subject/action/resource decision; an external HTTP PDP and Grant lookup are not implemented.

The subject is a verified AccountId of type `mikaki-account`; the resource is `mikaki-vault-attribute` with ID `vault-attribute:<owner>:<attribute>`. Allowed owner actions are `vault.attribute.read-ciphertext`, `vault.attribute.read-owner-envelope`, `vault.attribute.write`, `vault.attribute.delete`, `vault.attribute.share-system`, and `vault.attribute.revoke-system`. Unknown actions and service principals are denied. This uses the [AuthZEN 1.0](https://openid.net/specs/authorization-api-1_0.html) information model, not demonstrated external PDP interoperability.

An attribute name has 1–64 lowercase ASCII letters, digits, hyphen, or underscore. PUT accepts version 1 base64url ciphertext (up to 24 KiB) and owner envelope (up to 8 KiB). R2 stores immutable ciphertext at a random key; D1 stores its digest, head, revision, and owner envelope. GET verifies the stored blob digest. The server cannot verify client decryptability.

The browser creates a random 32 byte data key per attribute/revision and encrypts content with AES-256-GCM. Ciphertext bytes are `0x01 | nonce(12) | ciphertext+tag`. It derives an AES-256-GCM wrapping key from WebAuthn PRF output with HKDF-SHA-256. The owner envelope contains version, credential ID length and ID, 32 byte PRF input, 32 byte salt, 12 byte wrap nonce, and 48 byte wrapped data key. HKDF context binds origin, attribute, and credential; both AEAD AADs bind origin, attribute, and revision. PRF output and data key never go to the server. A different origin, lost passkey, or PRF incapable passkey cannot directly decrypt; rewrapping and recovery are still missing.

Creation requires `If-None-Match: *`; update/delete require `If-Match: "<revision>"`. Writes require same origin `Origin` and a 43 character `X-Operation-ID`. The same ID and request are idempotent; a different request with the same ID returns 409. Recheck revision, quota, SSO, credential, and account at conditional D1 commit. Deletion is a versioned tombstone. Limits: 32 attribute IDs per account and 20 writes per rolling 60 seconds. Daily GC removes unreferenced R2 blobs older than 24 hours; retry records are gradually removed after 90 days. D1/R2 cannot commit atomically, so orphaned blobs may remain until GC.

## System recipient sharing (disabled by default)

A user supplied `name` remains a Vault attribute, not mandatory account registration data or a verified legal name. The unlocked device can wrap only that attribute's data key for a dedicated UserInfo system principal, in addition to the owner's envelope. That principal could decrypt the shared attribute by itself; call this explicitly server readable for that purpose. Never wrap a Vault root/collection key or reuse an OIDC signing key.

Migration `0008_vault_attribute_sharing.sql` adds a recipient envelope, versioned system Grant, immutable share audit, and D1 policy. It was applied in production on 2026-09-24 with sharing disabled and a seven-day Grant TTL. The owner can approve sharing of the saved `name` after PRF unlock only when an operator enables the policy. The browser checks recipient-key continuity, unwraps the existing data key, creates the ML-KEM envelope, and clears the data key. The OP Worker checks SSO, same origin, attribute revision and ciphertext digest, active recipient key and directory revision, policy revision, and operation ID. Before the D1 write, it asks the claim Worker over a service binding to open the envelope with its Secrets Store seed and validate the exact stored ciphertext. Only a success status crosses back; no data key or plaintext does. An atomic D1 batch then stores the envelope, Grant, and audit. A stale revision or changed key fails closed. Revocation is an owner action; a Vault update or policy change revokes an active Grant. The local Rust and workerd paths, plus [Chromium approval/revocation UI](../local/conformance/vault-share-browser.test.ts), have been tested. A synthetic product envelope was verified with the live seed without recording a Grant. The full production owner flow and recovery remain activation gates.

Migration `0010_vault_claim_release.sql` adds a disabled RP release policy and per-account, per-client `name` consent records. A release binds the current attribute revision, system Grant version, client revision, and app connection Grant version, and has its own version, expiry, and immutable audit. An owner can grant or revoke it from Vault with an active passkey SSO session. D1 triggers reject a grant without current sharing, an active private-key client, and an active app connection; changing the system Grant, RP registration, app connection, policy, or account state revokes active releases. The Vault UI lists only already-connected RPs. A system Grant alone does not authorize any RP to receive `name`. AuthZEN makes an access decision; it is not key material or the consent ledger. A normal OIDC access token gives no Vault permission.

This is only the consent ledger and owner UI. Authorization requests still accept only `openid`; tokens do not carry `profile`; UserInfo still returns only `sub`. Keep the RP release policy disabled until the request scope, token binding, claim Worker decryption, and live release check are implemented and tested together.

The [recipient key and envelope format candidate](vault-recipient-envelope-format.md) specifies byte-level identity, suite, context binding, and the interoperability gates for `AttributeRecipientEnvelope`. Its frame is accepted by the disabled system-sharing path, but no production envelope has been written.

An attribute update revokes the old system Grant. A new revision requires the owner to share again; an absent matching envelope must stop UserInfo release rather than reuse an old one. Future RP release must check both the system Grant and a live RP-specific ClaimRelease. For future cryptographic separation, reencrypt with a fresh data key for remaining recipients. Already released plaintext/key copies cannot be recalled.

Disabling a recipient key revokes its active Grants through migration `0009`, while retaining envelope and audit history. A replacement key needs a new owner-produced envelope and Grant; it cannot make the old frame usable again.

For an RP request, confirm the requested claim, client, and explicit RP specific release consent. The claim service receives verified account/client/attribute/revision/purpose, checks the PDP and current Grant, then unwraps only that attribute. Separately check `oidc.claim.release` and ClaimRelease. Return pairwise `sub` plus authorized claims in UserInfo, not the ID Token by default. Missing attribute/consent or PDP/key/storage outage must not produce a stale cached value; choose omission versus temporary error under a defined HTTP contract. Do not add `name` to Discovery until this entire path is implemented and tested.

Test envelope swapping across attribute, revision, service key, and purpose; concurrent revocation; absent RP consent; PDP failure; and conflicting operation ID reuse. Audit principal, attribute, purpose, client, versions, decision, and result without plaintext or key bytes. FileNode/JMAP uses a separate API/data model even if blob, quota, and audit infrastructure are shared. An optional `name` conformance warning alone does not mandate collecting or sharing it.
