# 連合E2EEメッセージングの方針

2026-09-22。異なるCloudflareアカウントへ配備した複数のsakimoriを連合し、DIDで識別する主体間でE2EEメッセージを交換する。これは合意した開発目標であり、プロトコル・暗号スイートの選定や実装が完了したことを示さない。

具体的な端末処理と配送契約は[実装仕様](implementation-spec.md)の第10・11節に定める。以下は背景方針として残し、矛盾時は実装仕様を優先する。

## 配備と識別

各sakimoriは、別々の運営者・Cloudflareアカウント・D1・R2・運用秘密情報を持てる。共通のCloudflare管理権限や共有DBを要求しない。インスタンス間配送は、同一アカウント内のService Bindingを前提とせず、認証されたHTTPSのプロトコル境界を設ける。

「アカウント」が指す主体を区別する。

| 主体 | 識別と役割 |
| --- | --- |
| Cloudflareアカウント | インフラの管理境界。CloudflareのアカウントIDをメッセージ上の利用者IDにしない |
| sakimoriインスタンス／運営主体 | インスタンスDIDで識別し、公開鍵と配送先を結び付ける |
| 個人Vaultの所有者／利用者 | 利用者DIDで識別し、端末の鍵や連絡先との関係を管理する |
| 端末・鍵 | 鍵ID・世代・用途で区別する。DIDごとに秘密鍵一つだけという設計にしない |
| アプリ内の主体 | アプリ内subject。利用者DIDとの結び付けには本人の許可を必要とする |

内部AccountId、端末ID、独自の会話・メッセージID等は[識別子方針](identifier-policy.md)に従いUUIDを基本候補とする。DIDは鍵・制御主体・配送先との関係に必要な箇所へ限定し、すべての内部IDをDIDにしない。

インスタンスと個人のDIDを分けることを設計案とする。一人一インスタンスで運用する場合も、配送サーバーの鍵と本人のE2EE鍵は分離する。DIDは識別子であり、実在人物の本人確認、受信許可、Vaultのアクセス権を自動的に与えない。

## DIDメソッド

`did:web`と`did:key`を候補とする。初回から両方の完全対応を要求せず、最初の実証で利用する一つの組み合わせと鍵形式を固定する。

| メソッド | 性質 | sakimoriでの設計上の扱い |
| --- | --- | --- |
| `did:web` | HTTPSでDID Documentを取得し、同じDIDの鍵・serviceを更新できる | インスタンスの識別・配送先の公開の第一候補。ドメインと文書配信者への依存を明示する |
| `did:key` | 公開鍵から識別子と文書を導出する。通常の文書更新・失効操作を持たない | 固定した鍵を識別する候補。配送先は別途、検証可能な形で結び付ける。鍵変更はDID変更として扱う |

`did:key`からHTTPS配送先が自動的に見つかると仮定しない。利用する場合は、招待などで渡す所有者が認証した配送先情報、世代・期限、変更手順を定める。独自の公開ディレクトリを無条件の信頼元にしない。

`did:web`は文書を更新できるが、その履歴の完全性や、変更が本人によるものかを自動的に保証しない。初回の鍵確認、既知の鍵の保持、変更通知・確認、キャッシュ期限を設計する。連絡先のDIDと鍵を確認する招待・指紋照合などを最初の接続手順の候補とする。

最初から任意のDIDメソッド・JSON-LD文脈の外部取得・任意URLの解決に対応しない。DID解決と配送先取得には、HTTPS、接続先の検証、リダイレクト制限、時間・サイズ・深さの上限、SSRF対策を設ける。

## 鍵の責任

| 鍵・情報 | 保持する主体と用途 |
| --- | --- |
| Passkey秘密鍵 | 認証器。WebAuthnログイン用。汎用のDID署名鍵・暗号鍵として利用できると仮定しない |
| PRF由来の鍵 | 本人の端末。Vault内の秘密情報を解錠する。サーバーや相手に渡さない |
| 利用者・端末のメッセージ用秘密鍵 | 本人の端末。選定するE2EEプロトコルに従って生成・更新する |
| インスタンス運用鍵 | sakimoriサーバー。配送要求などの認証用。本文の復号能力を与えない |
| アーカイブ鍵 | 本人の端末。受信済みの会話をVaultに保管する。通信のセッション鍵と分離する |

DID Documentの`authentication`、`assertionMethod`、`keyAgreement`などの用途を区別する。公開鍵が文書に存在することだけで、あらゆる用途に使えると判断しない。WebAuthnのES256限定はログイン用の方針であり、E2EEの暗号スイートを独自にES256へ合わせる理由にはしない。

## E2EEの境界

```text
送信者端末：宛先の鍵を確認し、暗号化・送信者認証
    ↓ 暗号文
sakimori A：送信待ちを保存・配送
    ↓ 認証されたHTTPS、本文は暗号文
sakimori B：受信箱に保存
    ↓ 暗号文
受信者端末：送信者と文脈を検証し、復号
```

E2EEの終端は利用者端末とする。サーバーAで復号してサーバーBへ再暗号化する構成を、利用者間E2EEと呼ばない。配送要求を認証したことと、メッセージを作成した利用者を認証したことを分ける。

配送・保存サーバーは本文を復号できない設計とするが、宛先・時刻・サイズなどのメタデータは見える。メタデータ秘匿や匿名配送は初期目標に含めない。

鍵配布も信頼境界に含める。サーバーに本文を保存しないだけでは、サーバーによる公開鍵の差し替えを防げない。初回の鍵の信頼と、その後の鍵の継続性を検証する。

サーバーがブラウザ用コードも配信する構成では、悪意ある配信コードや解錠中のXSSから平文を守れるとは保証しない。独立したクライアント配布や鍵透明性が必要かは、脅威モデルの拡張として別に判断する。

## 通信プロトコルの選定

DIDは暗号化メッセージの形式や配送・再送を定めない。MLS/OpenMLSを第一候補とし、実Wasmの技術検証を採用ゲートとする。DIDComm全体とMatrix homeserverは初期スタックに含めない。これは標準の端末暗号と限定した独自配送の組合せであり、Matrix等との相互運用を意味しない。

- 独自の暗号プロトコルやratchetを設計しない。仕様がある方式と、その必要範囲を実装する保守可能なライブラリを評価する。
- 送信者認証、宛先と会話への結び付け、リプレイ拒否、オフライン受信、鍵更新を具体的に定義する。
- 前方秘匿性（長期鍵の漏えい後も過去の通信を守る性質）と、侵害後の回復を要求するかを初期選定時に決める。DIDComm採用やHTTPSだけを根拠に、端末間のこれらの性質を保証しない。
- MLSは最初の1対1から評価する。Rust・Wasmでの実装規模、鍵の認証、永続化・クラッシュ回復を確認して採用を確定し、不合格ならvodozemac等を別途評価する。
- ライブラリの監査範囲、利用条件、Wasm対応、テストベクトル、状態保存とクラッシュ回復を確認する。適合性・相互接続性を検証していない形式を、標準対応と称しない。

プロトコルを選定するまでは、長期鍵へ毎回暗号化するだけの独自方式を製品用の仮実装として固定しない。

## 最初の配送範囲

最初の実証は、相互に招待・確認した二つのインスタンス、各一人・一つの有効なメッセージング端末、1対1の短いテキストに絞る。認証基盤の複数Passkey対応と、複数端末への同時メッセージ配送は別機能とする。端末追加時の鍵移行・失効・過去履歴の共有範囲は明示する。

- 宛先ごとの受信許可・ブロック、容量・要求頻度・本文サイズの上限を設ける。公開DIDを知っているだけで無制限に書き込める受信箱にしない。
- 永続的な送信待ちと受信記録、メッセージID、重複排除、期限、再試行を扱う。分散配送全体のexactly-onceを保証せず、再送があっても一つの受信メッセージとして扱う。
- HTTPでの受理、受信側での永続化、端末での復号、既読を区別する。送信者に返す状態と、既読情報を送るかどうかを仕様化する。
- 再送・順序入れ替え・長期オフライン・鍵更新中の配送・宛先移転を、選んだプロトコルと矛盾しない形で扱う。
- 認証状態と会話プロトコルの更新、D1とR2など複数資源への保存に跨る原子性を仮定しない。途中失敗でnonceやセッション状態を再利用しないようにする。
- 初期の接続先は明示的な許可制とする。公開連合、汎用探索、グループ、添付ファイル、自動転送は後から追加する。

## VaultとMCPとの関係

受信者は検証・復号した会話を、本人の許可に基づいて自分のVaultへ再暗号化して保存できる。通信で古い鍵を削除しても、意図的に保存した会話のアーカイブ鍵が漏えいすれば、その保存済み本文は読まれ得る。通信の前方秘匿性とアーカイブの長期保管を同じ保証として扱わない。

受信・保管はAIへの開示許可ではない。MCPには所有者が選んだ会話だけを提供する。相手のDID、配送インスタンス、受信本文は、AIの権限を付与・拡大できない。将来AIに送信させる場合も、読み取りとは別の委任を必要とする。

## 実装前に確定する事項と完成条件

実装前に、インスタンス／利用者のDID方式、配送先の認証方法、E2EEプロトコルと暗号スイート、初回の鍵確認、鍵の更新・紛失・侵害時の手順、履歴保管、配送状態を確定する。初期実証で採用しない方式は、必要になるまで実装しない。

最初の完成条件は以下とする。

1. 別々のCloudflareアカウントに配備した二つのsakimori間で、オフライン受信を含む1対1メッセージの往復ができる。
2. 両サーバーのDB・オブジェクト・運用鍵から本文を復号できず、ログにも平文・利用者秘密鍵が出ない。
3. 鍵や宛先の差し替え、送信者の詐称、改変、リプレイ、許可外の配送を拒否または明示的な鍵変更として検出する。初回信頼の仮定を別に示す。
4. 再送・順序変更・応答喪失・サーバー再起動で、二重表示や暗号状態の危険な再利用を起こさない。
5. 鍵変更・端末喪失・連絡先ブロック時の挙動が仕様と一致する。
6. 受信会話を個人Vaultに保管・復元でき、MCPへは別途許可した範囲だけが渡る。
