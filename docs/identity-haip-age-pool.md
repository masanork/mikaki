# HAIP age receipt pool

The provisioned Android Wallet can request two to eight age-only receipts in one explicit authorization and save them together. By default it uses sequential single-credential OID4VCI requests: every slot has its own fresh holder key, attester challenge, issuer nonce, key attestation, proof and encrypted request/response. An additional opt-in mode sends all independently attested proofs in one encrypted Credential Endpoint request, using a shared one-use issuer nonce. The Wallet still defaults to one receipt.

Enable only in an experimental deployment with the existing complete HAIP issuer/client/attester/certificate/encryption configuration, `IDENTITY_HAIP_AGE_POOL_ENABLED=true` and an age-only `IDENTITY_ISSUANCE_CLAIMS` profile. Discovery adds `mikaki_age_pool: {"max_size":8}`. Absent capability, mixed/raw profiles, oversized counts or unknown claim names fail before enrollment. The native Wallet also checks that the selected count fits its existing eight-slot inventory before starting. No production flag or device qualification is enabled here.

## Authorization and issuer budget

The native protocol freezes a `mikaki_age_pool` JSON string in authenticated PAR, containing `size`, the canonical `claims_json`, and optional `mode: "batch"` (omitted means sequential). Browser parameters cannot replace it. The review shows the requested count, format and age predicates. The issuer copies this budget into the existing grant's `holder_json` before approval, so it survives consumption/erasure of the PAR request. No database migration is needed.

The grant retains the immutable baseline sixteen-slot schema ceiling, but the runtime enforces the narrower approved budget. `holder_json` contains the versioned budget and up to eight previously issued holder thumbprints; raw credentials and proofs are not retained. Each request rejects an already issued holder or a holder equal to the client-instance/DPoP key. Receipt preparation still clips validity to document/source/signing-certificate/key-attestation deadlines (the native broker's holder attestation is at most sixty seconds).

A conditional D1 update checks the complete previous grant snapshot, count, live account/document/policies and unused nonce, increments exactly one slot and records the new holder. The existing trigger consumes that nonce. A second statement closes the access token at the approved count; both statements run in one [transactional D1 batch](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch). An error in closing rolls back the count, nonce and holder changes, and no prepared credential is returned. The result is determined from the consume statement, so a stale concurrent request cannot return another receipt. Ordinary grants without this extension retain their existing budgets.

The enabled age-pool policy includes a new client-policy fingerprint and the exact age profile. Withdrawal or profile changes block use of pooled PAR/grants while they differ from the bound policy. Older binaries compute the previous fingerprint and cannot redeem or use a pooled grant, even if they ignore an unknown request parameter. Retained deployment gates and migration inventories are unchanged.

## Native receiving and failure

After token exchange, the Wallet enrolls and verifies one independently attested holder per slot. It validates every received credential against the configured credential trust and exact age-only profile before acknowledging that slot in its protocol state. Only then can the next fresh holder be bound; previous holder keys cannot be rebound. The protocol closes locally at the requested count.

Receipts remain private in Rust until all slots succeed. The Wallet rechecks expiry, distinct keys, inventory capacity and cancellation before one complete encrypted inventory write. A partial/unknown response, failed attestation, changed profile, expired earlier receipt, cancellation or storage error stops the operation and discards uninstalled keys. Successfully issued server slots remain consumed; there is no background refill or automatic retry of an uncertain issuance. Only an explicit DPoP nonce challenge permits the existing bounded transport retry before successful issuance. Another attempt requires a fresh explicit authorization. Existing inventory entries remain available when a receive cannot be installed.

## Optional multi-proof batch

`IDENTITY_HAIP_AGE_BATCH_ENABLED=true` additionally requires the complete HAIP configuration, `IDENTITY_HAIP_AGE_POOL_ENABLED=true` and an age-only profile. Discovery then adds the scoped `mikaki_age_batch: {"batch_size":8}` capability. The native Wallet chooses `mode: "batch"` for an explicitly selected count of two to eight when that capability is present; it retains sequential receiving otherwise. The default remains one receipt. The owner review distinguishes one combined receive from sequential receiving. A batch request to an issuer without the flag is rejected at PAR. A new client-policy fingerprint prevents disabled/older issuers or changed profiles from redeeming batch grants. Changing this flag invalidates in-flight Wallet PAR/grants through that policy binding; it does not alter the approved budgets of ordinary grants.

The wire mode uses `age_pool_version: 2` in the existing grant, with either zero holders before issuance or exactly the approved number after issuance. Here `issuance_count` counts **endpoint operations**, so one successful operation records all N holder thumbprints and closes the grant at count one. The immutable schema ceiling is unchanged. Both `proofs.jwt` and `proofs.attestation` arrays are supported. JWT proofs each require a single-key attestation. A direct attestation may cover several holder keys, including all approved keys in one JWT; every attestation uses the same unconsumed nonce and every verified holder must be distinct from all other holders and the client-instance/DPoP roles. The format, claim profile and exact count remain frozen in PAR. Sequential or ordinary grants cannot be expanded into a batch.

Requests and responses must both be encrypted. All proofs, source policy and deadlines are checked before preparing every credential and the complete ciphertext. Validity is clipped to the earliest attestation deadline. The conditional grant update records every holder and consumes the common nonce; the transactional close then removes the access token. A closing failure rolls back all holders, count and nonce. Concurrent dispatch has at most one successful response. A validation failure consumes no issuance authority. A successfully committed batch with unknown delivery is never retried or replenished automatically.

The Wallet stages proofs privately in Rust, using a fresh attester challenge for each key under the common issuer nonce. It rechecks every attestation expiry before dispatch and before a permitted DPoP nonce retry. It validates the exact response count, ordered holder bindings, signatures, independent credential trust, age-only claims and deadlines before closing its local protocol and installing the complete inventory once. Missing, reordered, malformed or invalid final credentials discard the whole pending receive. Cancellation and installation retain the existing generation and storage checks.

Batch encryption has explicit limits: request plaintext 144 KiB / compact JWE 208 KiB; response plaintext (including decompression output) 128 KiB / compact JWE 192 KiB. The request allowance accommodates eight proofs at the native 16 KiB signing-input bound. Oversized ordinary/sequential requests retain the original 20 KiB / 32 KiB limits. Single-response limits are unchanged. No remote key resolution or plaintext fallback is added.

## Grouped direct key attestations

[OID4VCI Final Appendix D.1](https://openid.net/specs/openid-4-verifiable-credential-issuance-1_0.html#appendix-D.1) permits an `attested_keys` array for keys from the same key storage component; [Appendix F.3](https://openid.net/specs/openid-4-verifiable-credential-issuance-1_0.html#appendix-F.3) defines the direct `attestation` proof type. The experimental age-batch grant accepts one to eight such proofs with **exactly N verified distinct keys in total**, where N is the count frozen in PAR. For an eight-receipt grant, one attestation with eight keys, eight single-key attestations, or ordered groups of one, three and four keys produce the same eight-key issuance budget. Credentials follow proof-array order, then `attested_keys` order within each proof.

Each group is checked against the existing explicit-purpose attester roots, signature, time/nonce, storage/authentication policy and unsupported-status rules. Its key count cannot exceed the remaining approved count. Empty groups, invalid/private keys, duplicate identities within or across groups, excess/missing keys, another sender role, or any invalid later group reject the complete request before grant/nonce consumption. JOSE `kid` metadata cannot disguise a duplicate public key. Credential validity uses the earliest verified group deadline. Closing rollback, one-winner concurrency and encrypted aggregate byte limits apply unchanged.

The grouped verifier is a separate API used only by direct proofs under an explicit batch grant. Ordinary/sequential grants and JWT proof attestations still require exactly one attested key, including when the batch feature flag is enabled. The Android broker and native Wallet continue to enroll and attest each holder independently; this change does not infer a grouped hardware attestation or modify that enrollment policy. Synthetic JOSE/workerd tests verify both formats, single eight-key groups, mixed groups, every returned holder binding and all-or-nothing rejection/commit. External full-app/device interoperability and official conformance qualification remain pending.

## Qualification and privacy

Tests cover both formats, sequential and encrypted wire receiving with eight independently attested keys in the native protocol, exact two/eight-slot server budgets, concurrent final requests, D1 rollback on close failure, sender/holder-role separation, key reuse with a fresh attestation, disabled/changed policy, UI consent/count locking and existing receipt/consent regressions. Real Android Keystore, card and crash qualification remains under #117; the DF31 intake decision remains under #116/#208.

Local single-use retirement applies to each installed age-only receipt. This pool reduces repeat presentation of the same holder key/credential bytes through this Wallet; it does not establish cryptographic unlinkability. The issuer can correlate the authenticated issuance session, and shared provenance, evaluation/expiry times, issuer keys/certificates and small predicate cohorts remain correlation sources. Static assurance and `government_credential=false` remain unchanged; no qualified OID4IDA `verified_claims` are emitted.

The [OID4VCI 1.0 Final repeated-endpoint model](https://openid.net/specs/openid-4-verifiable-credential-issuance-1_0.html#section-14.3) and the [HAIP profile](https://openid.net/specs/openid4vc-high-assurance-interoperability-profile-1_0.html) remain the protocol baseline. The encrypted multi-proof request and `credentials` response follow the Final Credential Endpoint shape. Standard global `batch_credential_issuance` metadata remains absent because this capability is scoped to the custom PAR budget; ordinary authorization grants are unchanged. General external-wallet interoperability and device qualification remain separate work.
