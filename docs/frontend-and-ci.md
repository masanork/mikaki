# Frontend, localization, and quality CI

The local login and Worker-served login, Vault, administration, and registration-completion UI uses Svelte 5 and Vite. A shared Paraglide JS 2 catalog generates typed Japanese and English messages. Type checks use TypeScript 7 from the root `typescript` package. `npm ci` also installs the separately locked Svelte checker under `tools/svelte-check`; its compiler API uses the official `@typescript/typescript6` compatibility package, while `--tsgo` checks with TypeScript 7 through `@typescript/native`. Source-inspection scripts import that compatibility API explicitly. Handwritten Node scripts, local harnesses, and design probes use `.ts` files run directly by Node 26 and checked with `npm run check:node`. The Node configuration enables all TypeScript strict checks, including `noImplicitAny` and null checks. The Svelte UI also enables `noImplicitAny`. Generated Wasm and Worker glue remains JavaScript. See [project status](status.md) and current workflows for implementation evidence. The targets below are quality policy proposals, not proof that every gate is live.

## Frontend boundary

Keep initial screens focused on login, first client connection, account selection, credentials, and session/connection management. Use Svelte runes and small modules, native HTML controls, and shared design tokens. Serve static UI on the Worker origin while Rust handles protocol endpoints, final authorization, and cookies. The browser may display a server bound transaction but cannot decide identity or authorization. Locale changes must not recreate state, nonce, PKCE, or consent context.

Keep WebAuthn calls in a thin adapter. PRF output and key material stay out of component display state and persistent stores; ordinary login does not request PRF. Do not render user, client, or translation text as HTML. Test CSP, focus order, screen reader messages, cancellation, and retries in real browsers. Avoid external scripts on authentication/unlock pages.

## Implemented product UI checks

The Worker account screens use `ProductHeader.svelte`, the login base styles in `auth.css`, and `product.css` served at `/ui/product.css`. Logout is server-rendered from `logout.html`; its confirmation and revocation work without JavaScript. The same-origin `/ui/session-events.js` module additionally broadcasts a local Vault lock on logout intent and completion. The stylesheet is permitted by same-origin CSP; no inline style exception is added. [Login](login-ui-preview.md) and [product previews](product-ui-preview.md) show synthetic local evidence.

`npm run test:product-ui` exercises shared screen delivery, Japanese/English presentation, 375px wrapping, keyboard navigation, profile loading recovery, operation serialization, exact lost-response retries, and acknowledged commits followed by refresh failure. `npm run check:docs` checks local Markdown file/image destinations and heading fragments. `npm run test:vault-lifecycle` checks display lease deadlines, disposal, resume verification, and cross-tab logout. All three checks are represented in CI; the browser suites run through `npm run test:worker-browser`. PR CI's product screen journey also records source-mapped Chromium execution for the Svelte/TypeScript UI. `npm run test:worker-contracts` runs product registration/authorization/storage contracts before merge, and the connected Rust OP journey covers code exchange/replay and logout denial. See [coverage scope and failure artifacts](test-quality.md); screenshot capture is a manual review artifact. These checks do not qualify every assistive technology or prove intended-device PRF/production readiness. See [remaining product gates](product-quality.md).

## Localization

Support Japanese and English from the start. Choose the first supported `ui_locales` value, then saved user choice, `Accept-Language`, then Japanese default. An explicit UI switch changes the current transaction's presentation only; issuer, origin, redirect URI, and subject stay fixed. Validate supported BCP 47 tags. Set `html lang`; format dates/numbers with `Intl`, while comparison and signed timestamps remain UTC. Translate stable server error codes in UI, never raw exception strings. Pre-JavaScript error pages need both languages.

The shared `messages/ja.json` and `messages/en.json` catalogs also cover OP logout confirmation, completion, and invalid-request messages, plus Help navigation, articles, ticket forms, statuses, and user-facing errors. The Help Worker uses a request-scoped TypeScript catalog adapter; Rust article metadata references catalog keys. Help chooses explicit `lang`, its `__Host-help-locale` cookie, weighted `Accept-Language`, then Japanese, and sends `ui_locales` when starting OP login. OP logout preserves presentation across its confirmation POST and keeps the registered redirect and state when switching languages. Ticket subjects and replies remain user content. `npm run check:i18n` verifies catalog keys and placeholders, not hard-coded UI coverage.

CI should detect missing/extra message keys, parameter mismatches, empty translations, and hard coded UI strings with context aware linting. Test long pseudo translations, wrapping, button widths, and focus in both languages. Runtime fallback does not count as complete translation.

## Growth and coverage

Measure base/head under identical rules for handwritten Rust, TypeScript/Svelte, SQL, tests, docs, generated files, and bundled assets. Exclude generated/vendor lines from handwritten counts, while still measuring shipped bundle bytes. Review public APIs, largest files, dependencies, raw/gzip Wasm and frontend sizes, build/test duration, TODOs, unsafe/allow suppressions, and coverage exclusions. Treat 500 handwritten lines in a product file as a review signal and growth beyond 800 as requiring a reason, not an automatic split. Do not fail CI merely because total code grows.

Record measurement JSON, HTML, LCOV, graphs, commit SHA, toolchain, features, exclusions, and metric version as CI artifacts and Job Summary. PR jobs should not get write tokens for a metrics history branch. The README links to [codebase growth](../README.md) and coverage reports.

Rust line/region/function coverage is measured with cargo-llvm-cov and exported as JSON, HTML and LCOV. `npm run test:frontend-coverage` establishes a Node/V8 baseline for handwritten Worker UI TypeScript, including unloaded modules, with LCOV/JSON output. Svelte/browser source-mapped coverage and Vitest-based component measurement remain unimplemented. Rust regions are not branches. Proposed starting targets: auth/OIDC core 90% line and 85% region; handwritten frontend logic 85% line and 80% branch. Establish baseline against real implementation before enforcing. Coverage is evidence of executed code, not proof of security properties. Verify protocol invariants with dedicated tests, fuzzing, integration/browser cases, and failure injection.

CI should run format/lint/type checks, native and Wasm builds/tests where applicable, design/config validation, dependency audit, localization checks, code growth and coverage reports. Keep release gates tied to meaningful contracts and record toolchain versions and exceptions. See [contributing](contributing.md) and repository workflows for exact current commands.

Release verification also runs `npm run test:release` in PR CI and the reusable attested build. The latter creates and verifies `release-manifest.json` for both archives and the ordered migration bytes, then attests that inventory. The SQLite/object rehearsal summary is uploaded with normal artifacts. See [release and recovery](release-and-recovery.md) for scope, verification and remaining production gates.
The attested build also prepares both production-configured Wrangler bundles from those verified archives, verifies staged member and bundle hashes, attests the upload inventory, and distributes the prepared inputs. There is no Cloudflare upload in CI. Operators must compare actual uploaded version IDs and preserved bindings during activation.

The manual production smoke remains reachable without release inputs. When given both an expected Cloudflare Worker version ID and attested source commit, it fetches `/version` and authenticated `/ready` using the GitHub Actions `MIKAKI_READY_TOKEN` secret, rejects mismatches, a dirty-source build or failed readiness, and uploads a short comparison record. The local Worker readiness test exercises the positive path, unauthenticated short-circuit and missing-policy/key/Claim-schema denials; this version-aware smoke has not been run against production. It does not identify the archive bytes uploaded to Cloudflare or exercise a real owner transaction.
Pull requests also build the OP Worker and run `npm run test:worker-browser` in Chromium after the passkey preflight. The four account-page, Worker UI, Vault sharing, and enrollment browser tests, plus the logout localization and CSRF test, run on `main` inside the attested supply-chain build. This catches UI and enrollment regressions before merge while keeping attestation write permissions on the `main` job.
