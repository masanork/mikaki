# 同一インスタンスの暗号化チャット限定ベータ

2026-10-20。最初の提供範囲を、日本語の通常Vault画面から使う、同じ
Mikakiインスタンスの1対1テキスト会話に固定する。製品ホストの実装と
ローカル検証を行う段階であり、本番公開・実機合格を意味しない。

## この区切りで使える操作

1. 通常のSSOでログインし、既存のOwner Vaultを開く。
2. 「Chat」タブを選び、初回だけ明示的にブラウザー端末を登録する。
3. 自分の端末コードを交換し、相手の指紋を対面や電話など別の連絡手段で確認して入力する。
4. 「招待コードを作る」で公開コードを作成し、相手が取り込む。双方が未選択の確認欄を選んで承認する。
5. 「同期」で参加を確認し、テキストを送受信する。後続の受信も前景の「同期」で行う。
6. 同じブラウザーで開き直して同じ端末と暗号化された履歴を復元する。Vaultのロックで復号済み表示を消去する。

本文上限はUTF-8で4,096バイト。「サーバー受理済み」は既読を意味しない。
1アカウントにつき1台のブラウザーを登録する。複数端末、履歴の端末間転送、
バックアップからの復元、端末紛失時の新規登録はこのベータに含めない。
公開コードと指紋の交換は利用者が行い、アカウント検索・自動相手選択は行わない。

ローカルの公開インデックスにはOwner鍵のコンテキストに結び付く端末UUIDだけを置く。
秘密鍵・本文・MLS状態は既存のVault custodyと暗号化ジャーナルで保持する。
保存状態が欠ける・一致しない場合に、別の端末や鍵を自動生成して続行しない。
未対応の復旧は停止と説明をもって扱い、ベータ完了のために復旧の組合せを増やさない。

## 実装と有効化

- [通常画面のホスト](../crates/worker/ui/ProductChat.svelte)は[Wallet／Chatの入口](../crates/worker/ui/ProductWorkspace.svelte)で既に開いたOwner Vaultを受け取る。別のVaultやPRF認証を追加しない。
- [遅延読込みするクライアント](../crates/worker/ui/messaging/client.ts)、端末custody、ジャーナル、画面を`crates/worker/ui/messaging/`で共有する。検証プローブは同じ実装を再エクスポートする。
- [製品ルーター](../crates/worker/src/messaging_beta.rs)はCargo feature `messaging-beta`と`MESSAGING_BETA_ENABLED=true`の両方を必要とする。既定ビルド・無効時の`/messaging/*`は404で、メッセージ用スキーマや署名鍵を必要としない。
- 製品ルーターは上記の登録、指紋確認、招待、承認、配送、前景同期に必要なAPIだけを明示的に許可する。端末失効、会話の停止・再参加、端末鍵の切り替え、サーバー側blockは限定ベータへ公開せず404にする。完全な復旧実装と攻撃プローブは将来プロファイルの検証用に残すが、製品ホストからは到達できない。
- `/vault/messaging-config`は通常の所有者認証後に有効状態・同じHTTPS origin・公開署名鍵・登録済み端末IDを返す。署名鍵の秘密部分は返さない。ベータのauthorityは同一originの製品設定を起点とし、相手の鍵の承認には別経路の指紋確認が必要。
- [メッセージ用マイグレーション](../crates/worker/messaging-migrations/)は通常の本番マイグレーション一覧から分離する。`0001_messaging.sql`の後に`0002_beta_profile.sql`を適用する。後者は所有者ごとの端末スロットを1個に制限し、既存の複数端末データには失敗する。
- `MIKAKI_ISSUER`、独立したEd25519の`MESSAGING_ISSUER_KEY`、既存のDB・Vaultバインディングが必要。署名鍵の値をコードや実行ログに記録しない。
- クライアントとWasmはChatタブのロック解除後に読む。CSPのWasm実行許可もベータ有効時だけ加える。[CSPの仕様](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/script-src)に従い、通常画面の既定ポリシーを維持する。ブラウザー用JSとWasmはビルドごとの出力から`assets/chat/`へ生成し、ベータ有効時のみ静的アセットバインディング経由で返す。サーバーWasmへは埋め込まず、既存の容量上限を維持する。

## ローカル検証

```sh
npm run check:worker-ui
npm run check:messaging
npm run test:messaging-beta
```

ビルドは`crates/worker/build-messaging-beta/`へ出力する。これらのコマンドは
デプロイやリモートDBの変更を行わない。通常Workerとは別の成果物を実際の
main Workerルーターで動かし、通常Vault画面をブラウザーから操作する。

[製品ブラウザーテスト](../local/conformance/messaging-beta-browser.test.ts)は
通常のSSO/Vault認可、実D1/R2相当のworkerd、実OpenMLS/Wasm、実ジャーナル・配送を通す。
認証済みSSOとWebAuthn PRFのみをテスト用に設定する。端末コード・招待・承認・送信は
画面から操作し、平文の秘密状態をテストから注入しない。無効時、未認証、セッション失効、
初回の明示登録、双方向送受信、再読込み、ロック、別ブラウザーの保存状態欠落を確認する。
モバイル幅の表示とアクセシビリティの構造も確認する。さらに、許可した通常APIは製品経路へ
到達する一方、端末失効・停止・再参加・鍵切り替え・blockの全ルートと誤ったHTTP methodが
認証済みでも404になること、および対象外の操作が製品UIに現れないことを確認する。

APIは既存の永続的な流量制限を通る。ローカルテストでは多数の逐次ジャーナル処理が
同じ送信元に集中するためfixture内の予算を引き上げる。本番の負荷・流量設定を
このテストで合格とみなさない。

## 限定ベータ公開までの残り

| 区切り                         | 完了条件                                                                                           | 状態                   |
| ------------------------------ | -------------------------------------------------------------------------------------------------- | ---------------------- |
| 製品画面・通常ログインへの接続 | 上記の操作を同一製品内で完走し、再開・ロックを確認する                                             | 実装済み、ローカル検証 |
| 本番設定とリリース             | 対象環境、署名鍵と公開鍵、段階的なスキーマ適用、容量・流量制限、CI、ロールバック時の停止を確認する | 未完了                 |
| 実機での受入れ                 | 対象OS・ブラウザーの実Passkey/PRF、2人の送受信、再起動・ロック、保存状態欠落時の説明を確認する     | 未完了                 |

別インスタンス間配送、グループ、添付、Push通知、AI参加者、アカウント発見、
鍵の透明性や独立配布クライアントは別の段階とする。既知の追加復旧経路もこの区切りを
延ばす理由にしない。現在のベータは安全に停止できる範囲で提供し、公開ゲートを先に閉じる。
