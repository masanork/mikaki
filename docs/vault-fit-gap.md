# Vault protocol fit/gap and work backlog

**Baseline:** repository source and recorded evidence reviewed on 2026-09-28, with isolated Codex OAuth and Grok Bot product findings added on 2026-09-29. This backlog applies [ADR 0012](adr/0012-vault-protocol-boundaries.md) and the [protocol review](vault-protocol-review.md). Existing local tests are evidence, not a fresh full test run or production activation. Task IDs below are document references, not GitHub issue numbers.

The owner ciphertext API and the limited MCP snapshot/proposal adapters fit the revised boundary. Local first slices now connect an exact approved note to encrypted owner storage. The largest remaining gaps are real-device owner-key continuity/recovery and interoperable remote client authorization. Credential presentation and file synchronization are conditional product tracks, not prerequisites for every Vault or agent use case.

### VG-01 — Owner key continuity and recovery contract

**Priority:** first for general Vault expansion. **Depends on:** none.

- Specify whether the first supported case is the same synchronized passkey on a new device, a different authorized passkey, or both. Account login alone is not key recovery.
- Design an authorized owner-key rewrap/transfer flow. The current single credential-bound `owner_envelope` cannot simply be replaced by multiple independent envelopes without a storage/version decision. Choose a backward-compatible migration or a new explicitly versioned format; preserve old readable data until the transfer is proven.
- Define removal, device loss, loss of every usable key, and any protected recovery backup. Do not imply a new login credential unlocks previous ciphertext. Evaluate encrypted backups and real restore, not just upload success.
- Keep existing conditional-write/retry coverage; add transfer-specific lost-response, stale revision, tombstone/offline replay, and decrypt-failure cases. State the rollback guarantee and its limits rather than equating revision checks with malicious-store protection.

**Done when:** a real supported device A saves data, authorized device B restores it under the declared credential case, unauthorized/removed credentials are rejected for future operations, and a failed/interrupted transfer leaves a documented usable state. Evidence includes intended-device PRF behavior and a recovery drill; already obtained keys/plaintext remain outside recall guarantees.

### VG-02 — Typed attributes and provenance, separate from credentials

**Priority:** before adding targets beyond `name`. **Depends on:** VG-01 design for key references; schema definition can start immediately.

- Define an attribute schema/version contract, encoding/size limits, validation location, source/provenance, and treatment of unknown versions. Keep editable owner assertions, imported application data, and issuer-signed credentials distinguishable.
- Implement one concrete additional attribute or consented archive type selected for a real consumer; avoid a generic ontology or full conversation importer without a source/use case.
- Preserve credential artifacts and annotations separately if VG-07 proceeds. A content hash proves byte identity, not issuer identity or truth.
- Specify what metadata is visible to storage and what is authenticated inside ciphertext. Owner-client validation must not become a false server-side plaintext-validation claim.

**Done when:** two qualified client paths agree on schema/version and reject invalid or incompatible input without corrupting existing data; the UI and downstream consumers retain provenance and assurance level. Remote grants cannot silently expand to every new attribute.

### VG-03 — Domain operation ownership and adapter boundary

**Priority:** before a second adapter or encrypted agent write. **Depends on:** the selected VG-02 change schema.

- Map the existing attribute, system Grant, RP release, agent snapshot, and private-draft authorities. They can share policy interfaces and audit conventions but remain different capabilities; do not merge their grant records merely because all contain expiry.
- Define an attribute-change proposal operation independent of MCP: owner, target, base revision, exact normalized payload/schema, destination, expiry, proposer, decision, committed operation/result, and content retention/disclosure.
- Resolve [ADR 0009](adr/0009-rust-oidc-and-worker-stack.md) against the current TypeScript agent product state transitions. Either move the applicable transition ownership into a Rust domain boundary or record a narrow explicit exception. This is an architectural decision, not a request to rewrite every adapter.
- Keep transport authentication and domain authorization distinct. Provide contract cases that an owner UI/HTTP path and the MCP adapter can both exercise; retain existing snapshot/draft tests.

**Done when:** the proposal/decision/commit contract has one authoritative implementation, the state-owner decision is recorded, and changed payloads, wrong owners, stale approvals, expiry, revocation, and identical retries have the same outcomes through each supported adapter.

### VG-04 — Approved proposal to encrypted Vault commit

**Priority:** first new agent write capability. **Depends on:** VG-01, VG-02, VG-03.

- Add a distinct attribute-change proposal and owner review UI. Show the exact destination/value and current/base revision; keep the existing private-draft action distinct.
- On an authorized owner device, unlock the saved envelope, validate the approved value, encrypt a fresh revision, and commit through the existing conditional attribute operation. Define which plaintext copies are held during proposal review and for how long.
- Bind the pending approval to that exact storage commit. Prevent replay into another target/revision. Define the atomicity or recoverable commit/result protocol across proposal state, D1 metadata, and R2 blob upload; a lost response must not execute the change twice or leave a reusable approval after a successful write.
- Reject or explicitly re-propose on conflict. Changing the original attribute already invalidates current agent snapshot grants; make the resulting connection state visible instead of automatically re-sharing the new value.

**Done when:** a synthetic agent proposal is approved, saved as owner ciphertext, reopened by the owner, and recorded once. Reject-before-approval, altered payload, concurrent owner edit, changed credential/grant, failed upload/commit, and retry-after-lost-response cases preserve the documented result.

## Capability-specific delivery tracks

### VG-05 — OAuth onboarding and remote activation

**Priority:** required only for a shipped remote connector. **Depends on:** current snapshot service; VG-03/04 only if encrypted writes are offered.

- Define the MCP client registration/discovery profile, public-client PKCE support, exact callbacks, resource/audience/scopes, consent, access-token validation, expiry/revocation, and any refresh behavior. The existing confidential OIDC login profile is not this implementation.
- Bind OAuth authorization to the selected target/grant and decrypting-recipient disclosure. A client identity can be authenticated under the chosen profile, but it does not authenticate an arbitrary bot display name or isolate a shared computer.
- Check one real remote Codex flow and the intended Grok integration independently. Existing Codex stdio reads and Grok Build handshake evidence do not prove a remote Grok Bot connector.
- Complete recipient provisioning, recovery/rotation, service-binding isolation, abuse controls, migration/deployment review, and operational evidence. Operator key rotation currently requires owner re-sharing; retain that contract unless a replacement has been designed and tested.

**Done when:** a named supported client connects through the selected OAuth flow, receives only approved data, and loses future access on expiry/revocation; production activation has its own review/evidence. RAR and DPoP remain optional follow-ups based on client support and need, not automatic requirements for the first connector.

### VG-06 — Complete ordinary RP profile release

**Priority:** when a connected RP actually requires `name` or another profile field. **Depends on:** the existing system recipient and ClaimRelease ledgers; VG-02 for new fields.

The local implementation now binds the `profile` request scope through the code and token, rechecks live RP-specific release and system Grant state in the dedicated claim Worker, decrypts the current owner ciphertext, and records disclosure. Absent consent omits `name`; a missing recipient secret fails closed. Both Rust Workers and a disposable local Secrets Store pass positive UserInfo decrypt/audit, damaged-blob denial, audit-write failure, and later revocation. The actual Vault screen, unlocked with a test PRF, creates the system share and RP release and withdraws the latter. A disposable reference RP completes the authorization code and token flow, validates the ID Token and UserInfo subject, and observes `name` removal after withdrawal. Reapproval restores disclosure; a Vault revision update revokes old sharing/consent until the browser approves the new value. RP registration revision change also revokes release, and a new key revision, browser approval and code exchange are needed to restore it. A missing current R2 blob, a thrown Claim Worker transport error, and a claim-service 503 each make OP UserInfo return 503 without disclosure; after recovery, the current Grant is checked again. A broken D1 authority view also returns 503 and works again after repair. Deleting the disposable local Secrets Store key returns 503 without revoking otherwise active consent or Grant. Internal UserInfo failures carry `Retry-After: 5` and no token challenge; invalid tokens still use 401. A held OP-to-Claim-Worker request, revoked in the browser before the claim Worker begins, also returns only `sub` without audit. A deterministic post-preflight test uses the claim Worker's exact conditional-audit SQL after browser withdrawal. A separate conformance-only Worker build pauses after actual decryption; browser withdrawal then makes the resumed UserInfo request fail closed with no disclosure audit. Disabling the recipient key again revokes both Grants, including for a newly issued RP token. SSO and the initial saved ciphertext are fixtures. Qualify a name-using RP application with an intended passkey device and real-service D1/Secrets Store outage, latency and recovery behavior before enabling policy. The local Helpdesk RP has no feature that needs `name`, so enabling `profile` there would not establish a product use case. OID4VP does not remove this work for ordinary profile consumers.

The [local timeout probe](userinfo-timeout-review.md) found that caller abort does not stop downstream service-binding work. A hard OP deadline therefore needs a cancellation or audit-outcome contract before it can be safely enabled; current 503 behavior does not bound a stalled request.

**Done when:** a registered RP receives exactly the consented current profile claims under the documented scope, and ordinary `openid` login remains independent of Vault. No claim is released solely because a system Grant exists.

### VG-07 — Minimal credential-presentation feasibility probe

**Priority:** exploratory; adoption depends on a real verifier requirement. **Depends on:** VG-02 object distinction and a holder-key lifecycle design; use disposable synthetic keys before production recovery is complete.

Select one credential type, test issuer, independent verifier/wallet tool, credential-format revision, trust/status rules, and presentation flow. Import an issuer-produced synthetic credential, store its original proof/disclosures, and present the minimally requested claims after owner approval. Define a dedicated holder key, which is separate from the WebAuthn login credential and recipient keys. Test wrong nonce/verifier/key, replay, untrusted issuer, expiry/status, overbroad queries, and cancellation.

**Done when:** an independent verifier accepts the intended presentation and rejects the negative cases; the report names exact tested implementations/profiles/devices. Decide whether to adopt OID4VP and add VCI issuance/import next from that evidence. A fixture import can qualify the first presentation probe without building an issuer or every VCI flow.

**Bounded delivery, 2026-09-29:** the [synthetic membership presentation probe](oid4vp-probe.md) passes 28 scenarios against `@openeudi/openid4vp` 0.12.0. The subsequent [OID4VCI receipt probe](oid4vci-probe.md) passes 42 scenarios with `@openid4vc/openid4vci` 0.6.0, including receipt → encrypted import → presentation. Reports separate independent-library and Mikaki policy checks. Exact issuer artifacts and dedicated holder keys have separate in-memory AES-GCM envelopes; approved presentation discloses only membership status. Trust/status and code/token/nonce authority are synthetic fixtures. Full external applications, network/TLS, real devices, recovery and product activation remain unqualified; these adoption gates keep VG-07 open beyond the bounded slices.

**Separate network evidence:** [OIDF Suite 5.3.1](oidf-conformance-2026-09-29.md) now checks issuer metadata over HTTPS and an independent verifier component against its emulated wallet: seven negative modules PASSED and two accepted positive modules REVIEW. The latter uses a distinct PID/`redirect_uri` profile. This closes neither membership receipt over TLS nor actual wallet-application E2E, DPoP/client-authentication, issuer trust/status, hardware keys or recovery gates.

**DPoP extension:** [45 component/policy and 11 HTTPS scenarios](fapi2-readiness.md#delivered-dpop-slice) now qualify synthetic anonymous membership receipt with sender-bound tokens over certificate-verified loopback TLS. Exact encrypted import and minimal presentation still succeed with a separate holder key. The product OP separately adds [shared Rust/D1 replay and token binding](fapi2-readiness.md#delivered-shared-rust-and-d1-authority), with UserInfo enforcement and cross-instance/reload/outage regressions. Full VCI applications, product nonce lifecycle, PAR/FAPI contracts, intended devices and holder recovery remain open.

### VG-08 — FileNode rights and independent-client probe

**Priority:** exploratory; adoption depends on a named file client/use case. **Depends on:** none for the profile decision; VG-01 if encrypted owner-file sync is selected.

Choose ordinary server-readable files or encrypted owner objects explicitly, pin the FileNode draft, and write the rights/capability map. Reconcile inheritance, ancestor visibility, rights-change reporting, content/blob authorization, and fine-grained Mikaki operations. Select an independent client that supports the target profile, or record its absence and reconsider WebDAV/another wire contract; a custom SDK client is weaker evidence. Probe basic nodes/blobs, conditional writes, idempotency, visibility loss, and cursor resync. Do not announce a standard capability before its semantics are implemented.

**Done when:** the wire/encryption profile and client choice are recorded from evidence. If adopted, implement the minimal qualified file service and expose MCP tools only over its domain operations. Broad filesystem features, Solid adoption, and a second ACL store are not implicit deliverables.

## Execution order and scope

The first delivery should be **VG-01 → VG-02 → VG-03 → VG-04**: key continuity, one useful schema, an authoritative proposal contract, and one owner-approved encrypted change. Do not build FileNode or a credential issuer to deliver this write path.

VG-05 can proceed from the current read-only remote slice when remote connection is the product priority; it need not wait for write capability. VG-06, VG-07, and VG-08 are independent consumer-driven tracks. Their design/probes can overlap, but each needs a named consumer and its own adoption decision before a broad implementation.

Keep the existing storage and MCP slice. Do not remove the isolated snapshot cipher merely to make all recipient formats identical, and do not introduce a universal grant/root-key abstraction as a prerequisite. Qualify each key/envelope purpose and lifecycle; rationalize formats only under a separately tested migration. An external AuthZEN PDP is likewise conditional on a concrete policy-sharing need, not required solely because the current owner evaluator uses its information model.

Before any production rollout, reconcile dated [status](status.md), [roadmap](roadmap.md), and runbooks with the exercised environment. Several older rows intentionally retain earlier limits; completed implementation tasks and later evidence must not become new deployment claims. The remaining login/device/RP/logout release gates still apply independently of this protocol refit.
