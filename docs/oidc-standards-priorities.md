# Additional OpenID and OAuth standards for Mikaki

Reviewed 2026-09-30. Mikaki's value is owner-controlled encrypted data, explicit disclosure to connected applications and agents, and a clear distinction between self-entered attributes and issuer-backed credentials. A standard is worth adopting when it improves one of those journeys with a named counterparty. The existing [protocol review](vault-protocol-review.md) remains the responsibility boundary: OIDC UserInfo releases ordinary profile claims, OID4VCI/OID4VP handle credential receipt/presentation, OAuth authorizes continuing API access, and MCP adapts agent operations.

| Candidate | Product value and current fit | Decision / adoption gate |
| --- | --- | --- |
| [AuthZEN Authorization API 1.0](https://openid.net/specs/authorization-api-1_0.html) (OIDF Final) | A standard PEP–PDP request for subject, action, resource and context could give the Vault, UserInfo claim Worker, agent MCP and a future FileNode service a consistent decision interface. Owner Vault checks already use the AuthZEN information model locally; no external PDP interoperability has been shown. | **Prepare an internal contract now; expose the wire API when policy sharing across independently deployed PEPs needs a qualified PDP.** Use the same authoritative grant and policy records. Bind evaluated IDs to verified principals, immutable target/revision and current grant state; deny on unavailable/malformed PDP responses; recheck inside the side-effect transaction. Discovery/search must not leak private resource existence. The PDP does not grant decryption keys, record consent or make a prior allow durable. |
| [OAuth Rich Authorization Requests, RFC 9396](https://www.rfc-editor.org/rfc/rfc9396.html) (IETF) | `authorization_details` can express an agent request for an exact operation, target, source revision and purpose more clearly than `read`/`propose` scopes alone. Current agent OAuth uses preregistered clients, scopes and one selected snapshot grant. | **Optional one-snapshot profile locally implemented; real-client qualification remains.** The bounded Mikaki type validates unknown fields/types, shows the request in owner consent, and binds the selected grant's source revision. Live grant and source checks remain authoritative at each call. This is an application-specific rights schema, not a generic Vault access standard. |
| [OpenID Connect for Identity Assurance 1.0](https://openid.net/specs/openid-connect-4-identity-assurance-1_0.html) (OIDF Final) | `verified_claims` separates verified identity attributes and verification metadata from ordinary OIDC claims. Mikaki already distinguishes self-asserted notes and issuer-produced credentials, but has no product-grade issuer trust/status or RP release of verified claims. | **Adopt only for a connected RP that explicitly needs verified identity through UserInfo.** Complete ordinary consented UserInfo release first; map an accepted credential and its issuer/trust/freshness evidence without relabeling owner-entered data as verified. Request/release selected claims with a separate consent contract. OID4VP remains preferable when the RP wants direct wallet presentation and selective disclosure. |
| [Shared Signals Framework / CAEP](https://openid.net/wg/sharedsignals/specifications/) (OIDF) | Standard security-event delivery could tell independent RPs or agent services about session or credential risk changes. Existing managed RPs use Back-Channel Logout and a session lease; the agent service checks live grants and token state. | **Defer until an independent receiver needs continuous risk signals that logout/live checks cannot convey.** Then specify exact event/subject mapping, receiver trust, ordering, replay, delivery and privacy. Do not treat an event as recall of already disclosed plaintext. |
| [OpenID Federation 1.0](https://openid.net/specs/openid-federation-1_0-final.html) (OIDF Final) | Trust chains and metadata policy could help a multi-issuer or multi-RP network, including credential ecosystems. Current clients are operator-registered and the wallet probe has no real trust network. | **Defer until a named federation and trust anchor are selected.** A trust chain would qualify entities/metadata, not by itself prove an individual's claim or replace credential status checks. |

## Near-term sequence

1. Qualify the locally passing, default-disabled owner-consented `name` UserInfo path with a named RP application, intended passkey device and production operation. The actual Vault screen and both Rust Workers pass the local browser approval-to-reference-RP UserInfo Secrets Store regression with a test PRF and seeded SSO; keep self-asserted provenance visible and do not advertise unsupported `claims` selection or `verified_claims`.
2. Qualify the locally implemented, optional one-snapshot RFC 9396 `authorization_details` type with a named agent client; the existing scoped grant still works when a client cannot send it.
3. Qualify one real credential issuer, wallet and verifier, then decide whether its RP needs OID4VP presentation or [verified claims through OIDC UserInfo](identity-assurance-adoption.md). Do not advertise `verified_claims` until that concrete profile passes its issuer, subject, status and consent gates.
4. Write shared AuthZEN-shaped *decision test vectors* for current owner ciphertext read, RP claim release, agent snapshot read, and owner-approved note commit: allow, stale revision, revoked grant, wrong recipient, missing context and backend failure. Introduce an HTTP PDP only if an independent policy-sharing need appears. Add federation/SSF only when the selected counterparties provide a matching trust or event network.

AuthZEN's [single and batched evaluations](https://openid.net/specs/authorization-api-1_0.html) are network decision interfaces. OAuth RAR describes requested/granted authorization. Identity Assurance describes verified identity claims. Their different roles are deliberate: sharing a policy vocabulary does not turn an OAuth token, an AuthZEN allow result, a VC presentation and a Vault ciphertext envelope into interchangeable authority.
