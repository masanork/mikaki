# Tauri client authentication decision review

**Status:** ordered architecture recommendation, 2026-09-30. The normal OP has a local public native-client **server slice**: operator registration with exact HTTPS or port-varying loopback callback, `none` token endpoint authentication, required S256 PKCE, one-use code exchange, and replay handling. The Tauri desktop client has a local UI and system-browser loopback flow with callback and ID Token validation. The Android and iPhone client has an app-claimed HTTPS callback handler with the same transaction and ID Token checks. A separate local-only mobile Vault preview now binds owner consent, an attribute-specific grant, DPoP Token, and ciphertext read. Its DPoP private key is stored by Android Keystore or iPhone Secure Enclave, while the token remains in Rust memory. None of these flows has been exercised against a signed installed app and registered production OP; native PRF remains unimplemented.

## Distinguish the roles

Mikaki is an OIDC provider (OP) for registered relying parties (RPs). It uses a WebAuthn Passkey to authenticate a person during an authorization transaction. The owner Vault is a same-origin Web application and currently authorizes through the `__Host-op-sso` Cookie; its page returns 401 without that session. Vault unlock separately calls WebAuthn PRF in the owner page. An ID Token or Access Token does not create a Vault session or provide PRF output. See [OIDC login](oidc-login.md), [Vault design](personal-vault.md), and the [Vault owner check](../crates/worker/src/vault_attributes.rs).

There are three different potential clients here:

1. **Tauri as a container for the first-party Mikaki Web application.** A remote `https://mikaki.tossa.app` document would retain the RP ID and same-origin fetch/Cookie behavior, assuming WebAuthn and PRF work in the target WebView. This is a WebAuthn owner session, not OAuth authorization of a native client. The current client now uses bundled local assets for its privileged UI and does not load the remote owner page. A separate first-party entry action to start an owner WebAuthn transaction may be needed for Vault usability, but it must reuse the existing ceremony/session authority. The current `/vault` entry starts owner login only for a live agent OAuth request; an ordinary unauthenticated visit returns 401. Do not start an unrelated RP's OIDC transaction merely to seed a Cookie.
2. **Tauri as a native OIDC/OAuth client.** Under [RFC 8252](https://www.rfc-editor.org/rfc/rfc8252.html), the app opens authorization in an external user agent, uses Authorization Code with PKCE, and receives the response through an app-claimed HTTPS link, private-use scheme, or desktop loopback. Its own WebView must not host the OAuth authorization request if claiming the RFC 8252 native-app best practice. Native apps are public clients unless an independently qualified per-instance confidential-client design is established. The current normal Mikaki OP only advertises `private_key_jwt`, registers server-side RPs with HTTPS redirects, and has no public native-client profile; the separate public [agent OAuth](agent-oauth.md) service is for selected MCP grants, not general OP or Vault access.
3. **A Web RP with a backend, displayed by Tauri.** The backend can use Mikaki's existing confidential OIDC profile. This is a conventional Web RP, but embedding its interactive authorization page in a native WebView is not the RFC 8252 pattern for a native app. It also does not itself deliver a PRF result to native code or grant the RP direct access to the owner Vault. Evaluate it only for a concrete backend-operated service, not as an implicit solution to native-app login.

The [FAPI 2.0 Security Profile Final](https://openid.net/specs/fapi-security-profile-2_0-final.html) is for confidential clients, authenticated PAR, and sender-constrained tokens. Mikaki's [FAPI 2.0 candidate](fapi2-readiness.md) uses `private_key_jwt`, PAR, and DPoP in an isolated profile. Packaging a shared private key into the Tauri binary does not make it a confidential client. FAPI 2.0 is therefore not the drop-in native-client answer. The native public-client OIDC path can still follow RFC 8252 and PKCE without a FAPI 2.0 claim.

## Connection to existing Vault

| Question | First-party WebView | Native OIDC client |
| --- | --- | --- |
| Interactive Passkey | WebAuthn on the Mikaki HTTPS origin, subject to WebView support and app/site association | In the external browser during OIDC authorization |
| Session held by | Mikaki WebView Cookie | Native client's token/session storage |
| Existing `GET /vault` | Works after the owner Cookie exists | Token alone is rejected |
| Existing WebAuthn PRF | Runs in the Mikaki WebView if supported | Browser PRF output is not sent to the app; a separate native PRF/unlock design is required |
| Standards claim | WebAuthn-based first-party Web app; no native OAuth claim | RFC 8252 native OIDC with a supported public-client registration and redirect profile |
| Principal gap | First-party owner entry and physical-device Passkey/PRF evidence | OP public-client support, callback/token lifecycle, Vault resource authorization, and owner-key access |

Apple documents Passkeys in `WKWebView` for an app-associated RP domain: [Supporting passkeys](https://developer.apple.com/documentation/authenticationservices/supporting-passkeys). Android documents Credential Manager support in WebView with feature checks and Digital Asset Links: [Authenticate users with WebView](https://developer.android.com/identity/sign-in/credential-manager-webview). Neither statement qualifies Mikaki's PRF extension or the Tauri wrapper on intended devices. Test the exact origin, associated-domain/Digital Asset Links setup, registration/assertion, PRF result, second-device reopen, cancellation, and session lock. A local Tauri asset URL has a different origin and cannot simply reuse `mikaki.tossa.app` as WebAuthn RP ID.

An external-browser OIDC completion will generally leave its browser Cookie outside the Tauri WebView. Do not copy the Cookie or turn an ID Token into `__Host-op-sso`. To give a native client Vault access, define a distinct OAuth-protected resource API with owner/attribute/operation scopes and conditional writes; its token would authorize the storage operation but still could not decrypt a PRF-wrapped owner key. Native holder-key and Passkey PRF access would need qualified platform APIs and a recovery contract. The current browser Vault should continue to use its existing Cookie and separate unlock unless that migration is deliberately chosen.

## Ordered evaluation for the native client

The recommended target has three separate authorities: OIDC authenticates the app's user, an OAuth resource grant permits specific ciphertext operations, and WebAuthn Level 3 PRF enables an owner device to decrypt. None of the three implies the next. Evaluate them in the order below; the first two are protocol designs and the third needs real-device evidence. The first-party owner page may remain available independently of the native API.

### 1. External-browser OIDC authorization

Register a **public native client** explicitly in the normal OP, initially by operator action. Do not reuse a confidential RP registration or ship a shared `private_key_jwt` key. Use Authorization Code with S256 PKCE, transaction-bound `state` and `nonce`, exact issuer/authorization-response `iss` checks, and ID Token validation. Use the platform's external browser surface, not the Tauri WebView: an app-claimed HTTPS callback on iPhone/Android and an ephemeral loopback port on desktop, with a private-use scheme only if needed. Record the client type independently of the callback URL. These are the [RFC 8252](https://www.rfc-editor.org/rfc/rfc8252.html) native-client boundaries; [RFC 9207](https://www.rfc-editor.org/rfc/rfc9207.html) defines `iss` checking.

Prefer separate registered client IDs for mobile and desktop initially. Their callbacks have different host/port rules, and the current OP derives pairwise subjects from registered sector hosts. If one logical client later spans several callback hostnames, settle a stable sector and `sector_identifier_uri` contract first; do not assume a dynamic loopback port can be listed in a static sector JSON file. [OIDC Core §8.1](https://openid.net/specs/openid-connect-core-1_0.html#PairwiseAlg) binds pairwise subjects to sectors. Treat the OP's internal account mapping, not equality of pairwise `sub` across platform client IDs, as the basis for its own resource authorization.

The normal OP now advertises `none` alongside `private_key_jwt` after the native registration and exchange paths were added. The FAPI deployment remains confidential-client only; the separate agent OAuth service does not supply the normal OP capability. Native registration accepts exact HTTPS callbacks or a loopback IP callback template with port `0`, a non-root path, and no query/fragment. The latter is restricted to `127.0.0.1` or `[::1]`, never `localhost`, and to a separate native client. The authorization request may change only the port. The registered template remains `authorization_code.redirect_uri` and its foreign-key target; `redirect_uri_actual` stores the ephemeral-port URI immutably. Token exchange requires an exact match to the actual URI. The native client must hold its PKCE verifier and tokens outside WebView script storage; begin without refresh tokens unless a concrete offline need justifies a [RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html) compliant sender constraint or rotation.

The server slice is exercised by `local/conformance/native-oidc.test.ts` and the public-token boundary test in `crates/oidc/src/token_boundary_tests.rs`. They cover exact HTTPS and ephemeral-port loopback callbacks, `iss` response parameter, wrong verifier or port, injected client secret, successful code exchange, and replay revocation. They use a synthetic existing owner session; they do not prove that an installed app receives a link, that a system browser completes Passkey login, or that a local desktop listener binds safely. The mobile Tauri callback handler requires exact path, state and issuer, rejects duplicate protocol parameters, and retains the PKCE verifier only in process memory for three minutes. A cold-start callback after the process has died has no matching transaction and requires login restart. The Worker association routes return 404 until `MIKAKI_IOS_TEAM_ID` and `MIKAKI_ANDROID_SHA256_CERT_FINGERPRINT` respectively contain the signed app's real identifiers. The [Tauri client README](../apps/mikaki-client/README.md) gives build and registration details. A verified HTTPS association response and installed-app link test are still required to qualify the native flow.

Operator registration is available as `node scripts/client-admin.ts --config <normal-OP-config> --remote no --action register-native --input <registration.json> --actor <name> --reason <reason> --apply yes` after migrations `0025_native_public_client.sql` and `0026_native_loopback_redirect.sql`. Mobile input is `{ "client_id": "<UUIDv4>", "sector_identifier": "mikaki-native.tossa.app", "redirect_uris": ["https://mikaki-native.tossa.app/oidc/native/callback"] }`; desktop input uses a separate client ID, sector `127.0.0.1`, and URI `http://127.0.0.1:0/oidc/callback`. The callback host must match the sector. The mobile callback host differs from the OP host because Safari generally keeps same-domain Universal Link navigation in the browser; see [Apple TN3155](https://developer.apple.com/documentation/technotes/tn3155-debugging-universal-links). Review the target DB and callback ownership before changing `--remote` to `yes`. The registration does not distribute a client secret or key.

**Gate:** deploy the second Custom Domain, configure the signed app identifiers, and register the new exact callback before any installed-client test. On each target OS, a real external browser completes Passkey login and returns to the app; valid ID Token claims and expected `state`/`iss`/`nonce` are accepted, while replay, intercepted callback, wrong issuer/client/redirect, missing PKCE, and app cancellation fail. This qualifies login only, not Vault access or PRF.

### 2. OAuth authorization for Vault ciphertext

Add a separately named Vault resource API and resource/audience-bound grants. The current `/vault/attributes/{attribute}` routes require the owner `__Host-op-sso` Cookie. An OIDC ID Token or existing UserInfo Access Token must not be accepted there, and browser Cookies must not be copied into the native app. Prefer [RFC 8707](https://www.rfc-editor.org/rfc/rfc8707.html) `resource` to select the Vault audience, short-lived Access Tokens, and [RFC 9449](https://www.rfc-editor.org/rfc/rfc9449.html) DPoP binding for this sensitive resource. DPoP proves possession of an app-instance key; it is not client authentication or proof of genuine app installation. Keep that key in platform-protected storage and enforce proof and replay checks at both token and resource endpoints.

The first-read implementation contract is [Native Vault OAuth](native-vault-oauth.md). Its key finding is that the existing Passkey login's generic `consent: true` and ordinary `app_connection` row do not express consent to a named Vault attribute. The Vault grant therefore requires a dedicated owner approval transaction before a Vault-audience code can be issued. The contract pins the exact attribute through an [RFC 9396](https://www.rfc-editor.org/rfc/rfc9396.html) authorization-details profile and keeps the current UserInfo token invalid at the Vault API.

The mobile Tauri preview now uses an installation P-256 key held by Android
Keystore or iPhone Secure Enclave. Kotlin and Swift return only public
coordinates and DER signatures to Rust; Rust verifies each signature against
the advertised JWK and converts it to JWS ES256 form. The Vault Token stays out
of WebView storage. The app verifies the OIDC ID Token and granted details
before a DPoP ciphertext GET. The preview is gated in the app build and OP
configuration. Android hardware backing varies by device, and iPhone's
Secure Enclave requires a physical device. The generated iOS entitlement lists
`applinks:mikaki-native.tossa.app`, but no signed-device or full Simulator build has
verified it yet. Signed-app association,
trustworthy consent display metadata, and real-device tests are still required
before treating this as an installed-client
security claim.

Start with an owner-consented **ciphertext read** grant for a named attribute or collection. Bind the grant to the internal owner, registered client, resource, allowed operation/target, expiry, and revocation version; scopes alone do not identify the exact object. The API maps a validated token to its owner internally and returns ciphertext plus the corresponding owner envelope, never PRF output or plaintext. A future write grant additionally needs `If-Match` revision, operation-ID retry rules, audit and the existing recovery gate. Keep current Cookie routes as the first-party owner interface; share the storage state-transition authority rather than introducing independent versions of the same record.

**Gate:** native ciphertext read succeeds only with the matching live Vault grant, audience and DPoP key. Wrong audience, expired/revoked grant, other owner/attribute, Bearer substitution, proof replay and unauthorized writes fail. No successful token test counts as decryptability.

### 3. WebAuthn Level 3 PRF and local decryption

[WebAuthn Level 3 PRF](https://www.w3.org/TR/webauthn-3/#prf-extension) evaluates a credential-specific function and returns client-side output; it does not define OAuth authority or a server-verifiable Vault grant. The present Vault format encrypts each attribute with a fresh data key and wraps that key under an HKDF/AES-GCM key derived from the PRF output. Its owner envelope includes the credential ID and PRF input. The current browser evaluates PRF with user verification and a local random challenge; it does not submit that assertion as a new server login. Do not send PRF output through an OIDC redirect, token, URL, server API, log, or unrestricted Tauri command.

First probe the **first-party HTTPS Vault page** inside Tauri on macOS, Android and iPhone. Establish its own legitimate owner Cookie session, then test a real saved record and exact PRF result under the registered Mikaki RP ID. An external-browser OIDC session does not provision that WebView Cookie. App/domain association and WebView Passkey support need target-device qualification; a local Tauri asset origin cannot silently assume the Mikaki RP ID. Keep remote page script away from generic native NFC, Wallet and secure-storage capabilities under [Tauri's capability model](https://v2.tauri.app/security/capabilities/).

Only after that probe, evaluate native PRF calls and the same envelope format. Apple documents [native PRF assertion inputs](https://developer.apple.com/documentation/authenticationservices/asauthorizationpublickeycredentialprfassertioninput-swift.struct); Android native provider and WebView behavior need separate evidence. Compare output-derived decryption against the existing Web page for the same credential/input and distinguish unsupported PRF, missing credential, user cancellation and wrong envelope. If a platform cannot open the record, keep the owner HTTPS page or use an explicit same-account transfer/recovery flow; do not invent a token-to-key bridge. The present [passkey transfer](vault-passkey-transfer.md) replaces one attribute's owner envelope at a new revision, and real-device continuity plus loss recovery remain open.

**Gate:** on intended real devices, save on one device and reopen on another using the documented credential/envelope path; verify UV, PRF availability, foreground/background lock, failed decryption, transfer, rollback/conflict and loss behavior. Browser mocks and desktop compilation do not satisfy this gate.

This ordering selects a standards-based login direction and bounded Vault-resource contract before app commands or broad PDS/Wallet UI work. It does not assert that the first-party WebView is an RFC 8252 OAuth user agent or that the public native client satisfies FAPI 2.0.
