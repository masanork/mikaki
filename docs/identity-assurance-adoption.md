# Identity Assurance adoption boundary

Reviewed 2026-09-30 against [OpenID Connect for Identity Assurance 1.0](https://openid.net/specs/openid-connect-4-identity-assurance-1_0.html). Mikaki does **not** currently emit or advertise `verified_claims`. The optional OIDC `claims` request parameter remains unsupported. The ordinary owner-entered Vault `name` is self-asserted, even when the owner consents to its release through UserInfo; signing a Mikaki ID Token or serving it over HTTPS cannot turn it into a verified identity claim.

The first locally implemented UserInfo profile path now binds `profile` to the authorization code and token, checks an RP-specific ClaimRelease and the current system Grant, decrypts the exact current owner ciphertext in the dedicated claim Worker, and writes a disclosure audit before returning `name`. A paired-Worker local test confirms that missing RP consent returns only `sub` and a missing recipient secret fails the UserInfo request. A separate disposable local Secrets Store test uses both real Rust Workers and the actual Vault screen. The browser unlocks a pre-saved name with a test PRF, shares it with UserInfo, grants RP-specific release and later withdraws it. Its reference RP completes authorization-code issuance, token exchange, ID Token validation and UserInfo lookup: it receives `name`, then only `sub` after withdrawal. SSO and the saved ciphertext are fixtures; a real passkey device, named RP application and production operation are not yet qualified. The policy defaults remain disabled. This path does not use `verified_claims`.

Identity Assurance needs a named RP, issuer and trust framework before enabling a wire profile. For each requested claim, record and check the issuer artifact, subject/holder binding to this Mikaki account, signature and key status, credential expiry/status at release time, verification method/time under the selected trust framework, the selected RP's exact request, and fresh owner consent. Map only supported claim names and verification metadata; reject an unknown framework or unverifiable source. A saved credential's original bytes and provenance remain separate from the projected OIDC response. A claim already copied to an RP cannot be recalled.

| Source and evidence | UserInfo behavior |
| --- | --- |
| Owner-entered `name` and live RP ClaimRelease | Ordinary `name` under `profile`, if the disabled policy is intentionally enabled and the claim service succeeds. Never `verified_claims`. |
| Imported file, agent suggestion, or unsigned metadata | No `verified_claims`, regardless of a displayed source label. |
| Issuer-produced credential without a qualified trust framework, holder/subject binding, or live status check | No `verified_claims`; preserve it for a separate wallet/presentation flow if valid there. |
| Qualified issuer evidence, named framework, selected attributes, current status and RP consent | Candidate for a future `verified_claims` UserInfo profile and OIDF conformance run. No such product path is advertised today. |

Implementation gate: select a real issuer/credential format and RP, define an exact trust-framework identifier and claim mapping, implement request parsing and per-claim consent, then test wrong issuer, wrong holder, expired/revoked credential, stale source, excessive claim request, wrong RP, and missing/withdrawn consent against an independent RP. Only after this passes should Discovery advertise `verified_claims` or `claims_parameter_supported: true`. OID4VP remains the direct wallet presentation route when the verifier wants the holder's proof rather than an OP-issued identity statement.
