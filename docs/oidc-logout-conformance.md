# RP-Initiated Logout conformance run

On 2026-09-27 JST, the local Mikaki OP fixture was tested with OIDF Conformance Suite 5.3.1 using the `oidcc-rp-initiated-logout-certification-test-plan` plan. The static client used Authorization Code flow and a Chromium virtual passkey. The final complete run was plan `PXI54vyEHYG0z`.

| Result | Modules |
| --- | --- |
| `PASSED` (3) | Discovery endpoint verification; standard RP-initiated logout; logout without `state` |
| `REVIEW` (8) | Invalid redirect URI, modified ID Token hint, missing ID Token hint with redirect URI, no parameters, no redirect URI, only `state`, added redirect URI query, invalid ID Token hint |

All 11 modules finished. The eight `REVIEW` cases ask a human to inspect an error or successful logout page; this is not an automated pass or formal certification. The run `Qm9prAtPxjTPc` repeated those eight cases and uploaded screenshots after the logout request, including the completion page for successful cases. Their detailed records remain in ignored `local/generated/oidf-passkey-*.json` files, which may contain test credentials.

The suite exposed three implementation gaps: `end_session_endpoint` was absent from Discovery, `state` and `post_logout_redirect_uri` were incorrectly required, and the confirmation page's browser policies blocked its own POST or redirect. Those were corrected. A local Worker/D1 integration probe also verifies unregistered redirect and invalid hint rejection, no-parameter confirmation, same-origin POST, atomic rollback on injected D1 failure, concurrent duplicate POST, SSO/client-session revocation, and logout outbox snapshot.

The OP now accepts RP logout requests via HTTP POST, converting validated form parameters to a same-site GET confirmation so the browser can send its Lax SSO cookie. The Back-Channel delivery worker signs `logout+jwt` tokens and retries leased outbox items every minute. The local signing test verifies the JWS signature and required claims; the Worker/D1 probe verifies that a failed outbound attempt remains pending with an incremented attempt count.

After these changes, the standard RP-Initiated Logout module passed again in plan `3qVI0ntufGbl0` (module `VNdetLbJdh9sG1G`).

The Back-Channel Logout plan passed both modules in local plan `FPztRpfv2FKWB`: Discovery (`WjnX5Le6YeoJiZi`) and RP-initiated notification (`GSBptXK9YyKOEcg`). The earlier attempt (plan `FAaW9v4CThyp0`) stopped before notification because the test harness could not reach the suite's HTTPS receiver. The suite certificate is issued to `localhost`, while the Worker addresses it as `suite-frontend`; Node's outbound fetch rejected the mismatch. Running the fixture on the suite's Docker network with certificate verification disabled **only for that local test process** let the suite receive and validate the Logout Token. This does not change production TLS handling or constitute formal certification.

The eight RP-Initiated Logout `REVIEW` screenshots in plan `Qm9prAtPxjTPc` were inspected locally. The three successful logout cases show 「ログアウトしました」. The five rejected-request cases show “Invalid logout request” and do not identify the invalid parameter. This is consistent with rejecting the requests, but the suite leaves the result at `REVIEW`; a certification reviewer must decide whether the generic error text satisfies the requested page evidence.

A source audit of the OIDF suite checkout at `daf33d61b` clarifies that [`REVIEW` is set when an image is uploaded](https://gitlab.com/openid/conformance-suite/-/blob/daf33d61b982d5d33d134b07e9a36f76176b3eff/src/main/java/net/openid/conformance/logging/ImageAPI.java), without automatic inspection of its content. The [negative-case modules](https://gitlab.com/openid/conformance-suite/-/blob/daf33d61b982d5d33d134b07e9a36f76176b3eff/src/main/java/net/openid/conformance/openid/OIDCCRpInitiatedLogoutBadIdTokenHint.java) fail if the OP calls the registered post-logout redirect URI and ask for a screenshot. Their summaries allow either an error page or user confirmation; the screenshot prompts ask for an error page identifying the invalid input. [RP-Initiated Logout §4](https://openid.net/specs/openid-connect-rpinitiated-1_0.html#ValidationAndErrorHandling) forbids post-logout redirection on error but leaves the page wording to the OP. The generic error page is therefore not, by itself, evidence of a protocol violation. The three screenshot-based success cases do not independently retry authorization with `prompt=none`; the standard case does. The suite image used for this run reported version 5.3.1 and may differ from the source checkout; its logged screenshot prompts matched those inspected in the checkout.

The [Back-Channel RP-initiated module](https://gitlab.com/openid/conformance-suite/-/blob/daf33d61b982d5d33d134b07e9a36f76176b3eff/src/main/java/net/openid/conformance/openid/OIDCCBackChannelRpInitiatedLogout.java) validates the notification's signature, claims, `sub`/`sid` correspondence, absence of `nonce`, post-logout redirect state, and failure of a subsequent `prompt=none` authorization. It accepts either arrival order for the notification and browser redirect. This passing module covers one successful delivery path; it does not exercise retry scheduling or receiver failures.

The test profile and manual-review requirements are described by the [OpenID Foundation OP logout testing instructions](https://openid.net/certification/connect_op_logout_testing/); optional request parameters and GET/POST methods are defined in [RP-Initiated Logout 1.0](https://openid.net/specs/openid-connect-rpinitiated-1_0.html).
