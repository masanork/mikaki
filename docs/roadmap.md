# Roadmap and design maturity

This page groups the project's intended stages. It is a direction of work, not a release promise. [Status](status.md) lists what has actually been verified or deployed.

| Stage                              | Intended outcome                                                                                                                     | Maturity                                                                                                                                                                                                                                                                                                                                                                 |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Passkeys and OIDC                  | Shared account, WebAuthn login, managed RP integration, session lifecycle, and browser-side PRF key protection.                      | Core paths exist in local tests and parts of the Worker; production integration and release gates remain.                                                                                                                                                                                                                                                                |
| Personal vault                     | Encrypt data on the client; store ciphertext and wrapped keys in IndexedDB and R2; recover on another authorized device.             | Owner-only storage components are deployed; one administrator saved and reopened a name with a real Passkey in production; cross-device/recovery and newer features remain unqualified. See [vault design](personal-vault.md).                                                                                                                                           |
| Selective UserInfo claim sharing   | Add a separate recipient-key directory, browser-side envelope, grant, and dedicated claim Worker.                                    | Generation-1 recipient key is provisioned and active; browser envelopes, system grants, and RP consent have local evidence and disabled deployed policies; production owner approval and UserInfo profile delivery remain open. See [claim sharing](vault-claim-sharing.md) and [key lifecycle](vault-recipient-key-lifecycle.md).                                       |
| Conversation archive               | Import conversations from participating applications with the user's authorization and provide cross-app access.                     | Encrypted v2 thread records and browser-local SQLite search exist; real-source ingestion, stable import/reconciliation and live federation remain open.                                                                                                                                                                                                                                                                                                                                                           |
| Federated messaging                | Start with one-to-one text delivery between two independently deployed instances, with DID-based identity and end-to-end encryption. | Future design; protocol and trust choices have gates. The [implementation spec](implementation-spec.md) contains the earlier staged design and acceptance gates. [Storage API](storage-api.md) and [Vault claim sharing](vault-claim-sharing.md) separate implemented slices from remaining proposals. [Crypto agility](crypto-agility.md) and [PQC rollout](pqc-rollout.md) describe migration conditions, not currently deployed algorithms or a committed rollout date.

New capabilities should have a concrete user need, state transitions, failure behavior, and verification plan before they add abstractions to the authentication core. A future container deployment would add an adapter around the same core; it is not part of the first release.

For the protocol refit, the [Vault fit/gap backlog](vault-fit-gap.md) sequences owner-key continuity, typed data, domain proposal ownership, and approved encrypted writes. Remote OAuth, RP profile release, credential presentation, and FileNode adoption have independent consumer-driven tracks; implementing every candidate standard is not a prerequisite for the common Vault path.

The [additional OpenID/OAuth standards review](oidc-standards-priorities.md) prioritizes completing consented UserInfo, then AuthZEN-shaped decision vectors and a client-driven RAR probe. Identity Assurance, Shared Signals and Federation have explicit RP or trust-network adoption gates.

The first VG-02 implementation is a typed encrypted owner note with strict client validation and self-asserted provenance; [its contract](vault-typed-attributes.md) records the local HTTP/browser qualification. The first VG-03 [proposal authority and owner review](vault-attribute-proposals.md) now have local HTTP/MCP/browser evidence. The first VG-04 [verified encrypted owner commit](vault-approved-commit.md) now has local fault/retry/recovery evidence; production activation and real-device qualification remain. Intended-device and recovery gates from VG-01 remain open.

Saved owner notes can now be explicitly selected for local read-only MCP export, with fresh PRF, saved-version checks and plaintext preview. Downloaded bundles/grants pass an actual stdio server/SDK read-and-revocation flow; remote targets remain name-only. This provides useful local AI context without requiring hosted-plugin distribution. See [the saved-note flow and copy boundaries](agent-integration.md#saved-note-local-read-flow-2026-09-29).

The first VG-05 [preregistered public-client OAuth profile](agent-oauth.md) now has local SDK/workerd/browser qualification. Owner Passkey login/return is implemented locally, and installed Codex discovery plus an accepted preregistered PKCE request are qualified. The isolated Codex CLI/App Server now qualifies token persistence, reads, scope narrowing and revocation against local workerd. Next qualify the deployed Codex endpoint and actual Grok Bot plugin requirements and complete operational activation evidence. Client metadata/DCR and refresh should follow those concrete requirements rather than be advertised before implementation.

Grok Bot qualification now has preparation/redaction tests in CI and an authenticated account-route observation: the inspected personal dashboard's Add action opens the public marketplace, with no private repository import controls observed. Establish a supported custom-plugin distribution route before hosted OAuth qualification; do not treat another login attempt or an unverified paid upgrade as that gate's completion. See [recorded account findings](grok-bot-integration.md#account-route-observation-2026-09-29).

Saved notes now have a separate [Passkey transfer UI](vault-passkey-transfer.md#saved-note-ui-2026-09-29), with local saved-content/new-key/retry/conflict qualification. Owner-facing source-revision/freshness and sharing status now have [local UI qualification](agent-integration.md#source-version-and-copy-freshness-2026-09-29). Structured MCP result schemas and source/access metadata now have [local stdio/HTTP/browser qualification](agent-integration.md#structured-mcp-results-2026-09-29). The bounded [OID4VP presentation](oid4vp-probe.md) and [OID4VCI receipt](oid4vci-probe.md) probes now qualify the same synthetic membership against independent protocol libraries, with 70 combined cases. Next select a named full issuer/wallet and qualify the Final wire profile over TLS. Intended-device PRF, holder recovery and hosted client activation remain separate gates. Grok Bot distribution work is deferred pending a concrete need.

The subsequent [OIDF HTTPS evidence](oidf-conformance-2026-09-29.md) adds credential metadata and emulated-wallet/verifier-component checks alongside current-build Basic/Config OP. A separate PID/`redirect_uri` component profile is exercised; full membership receipt and actual wallet-application E2E remain the next credential qualification gates.

For the native app, qualify the [Vault ciphertext, owner unlock, and device-recovery path](native-vault-oauth.md#local-revalidation-before-wallet-adoption) before using it as Wallet storage. Local Vault lifecycle, note, transfer, and Worker-contract suites pass, with signed Android ordinary OIDC callback now verified. Native Vault consent/ciphertext access, real-device PRF decryption, iPhone and second-device recovery remain open. Once that gate passes, start the Wallet compartment with one test-only issuer-backed credential type: receive through the selected OID4VCI Final profile, persist its exact signed artifact and separate holder key in purpose-bound encrypted records, display issuer/type/status separately from self-entered Vault notes, and require exact per-request approval for a single OID4VP presentation to a pinned verifier. Do not expose general import, unattended agent presentation, or production trust claims until independent full-app/network interoperability, issuer trust/status, and holder-key recovery are qualified.

The [product quality gates](product-quality.md) track responsive/keyboard/error behavior, documentation drift, operational readiness, and the remaining activation evidence. The [account and Vault UI](product-ui-preview.md) now shares the login design; local visual and interaction checks do not replace intended-device, assistive-technology, or production validation.

The [2026-10-03 Vault usage proposal](vault-product-model.md) prioritizes a single owner-key unlock, encrypted human/human and human/AI thread archives, and subsequently linked application/approval history. It distinguishes semantic threads/messages/workflow events, attributes and records from internal blob storage, and includes a fictional interactive preview. Live E2EE requires its own qualified endpoint/key/protocol boundary; chat assertions are not official receipts or decisions. The current per-item unlock, single-note slot and name-only remote sharing remain implementation limits; the preview does not qualify their replacements.
